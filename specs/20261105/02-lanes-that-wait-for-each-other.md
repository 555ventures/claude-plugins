# Lanes that wait for each other

## Intent
- You asked: plan roadmap 34 — the fan-out trial's design-sized findings: honour `depends_on` at PLAN, never lose or strand a stopped lane's work, land lanes as they finish, resolve a conflict in one dispatch, and stop lanes from rewriting locked Decisions.
- I will build:
  - PLAN (AUTO, explicit paths and `--pick`) holds a hardened spec whose `depends_on` names a spec that is not `done` on trunk, and the Waiting line says which dependency and why.
  - A lane that stops, waits or is dismissed gets a `wip(spec): <stem>` commit on its branch first; COMMIT folds WIP commits into the one build commit, so trunk never sees them.
  - `--mark planned` rebases a reused worktree onto trunk (WIP commit first); a conflict is left in progress for the lane's own `/spec:run`, which resolves a rebase at any step, moves `base`, and continues — a MERGE_READY lane goes straight into GATE and REVIEW in the same dispatch.
  - A `waiting` verb in both drivers: `run.js --mark waiting --on <spec>` for the lane agent, `fanout.js --mark waiting --lane N --on <spec>` for the orchestrator; a waiting lane leaves the active set and PLAN re-picks it once the spec is done.
  - WAIT lands a MERGE_READY lane as soon as it returns when no lane is sent back or mid-rebase; reports print the landed sha.
  - `run.js` refuses spec edits deterministically at GATE (another spec file, or the own spec's Decisions table) with an ESCALATE whose `revert` restores them, and gains `--mark unmet --decision <id> --why <text>` so an unmeetable Decision is a question, never an edit.
  - Prose and contract reconciled: fanout.md, run.md, doctrine.md, builder.md, reviewer.md, docs/v8/interface-contract.md, docs/v8/architecture.md; tests for every criterion.
- I will not touch:
  - `spec/scripts/block-worker-git.sh`: its blocked verbs stay; the driver, a node process, does every rebase and WIP commit, so no escape hatch is added.
  - File Plan overlap prediction or overlap-aware merge order (specs/20261103/15 D1 stands: git decides at landing); the `second rebase conflict` stop rule; the queue's data model.
  - A gate rerun counting as a repair (q152), lane count versus machine load (q153), migrating v7 spec bodies, the plugin version (ADR-0039 D4: bumped at release).
- Architecture or behaviour change: no — the fan-out driver's behaviour changes exactly as brief 34 specifies; no ADR is added or overturned (ADR-0039 D2 already presumes `depends_on` is honoured, and specs/20261103/15 D1 stands).

## Goal

A fan-out never builds a spec beside or ahead of a spec it depends on, a lane that stops for another lane keeps its work and resumes on the trunk that has it, a finished lane lands while the others are still building, a conflict costs one dispatch, and a lane that cannot honour a Decision asks instead of rewriting the spec. On niko-hub's batch 1 this would have run lane 4 alone, held the three dependents with a printed reason, picked them next with their worktrees rebased, and saved roughly 45 minutes of builder time plus two dismissals.

## Decisions

| ID | Decision | Why |
|----|----------|-----|
| D1 | PLAN honours `depends_on`. `eligible()` reads `frontmatter.depends_on` of every hardened candidate (an array; a scalar string is one entry); each entry resolves `rel(root, entry)`; an entry whose file does not exist on disk is ignored; an entry is satisfied when the root copy's `status` is `done`. In queue order, a candidate with an unsatisfied entry goes to `waited` with why `depends on <entry as written> (lane N this batch)` when that entry was picked earlier in the same walk, `depends on <entry> (draft — it cannot land in this fan-out)` when its status is `draft`, else `depends on <entry> (<status>, not done)`. `picked` is the first `config.lanes` satisfied candidates; `held` is unchanged. | ADR-0039 D2 tells planners to declare `depends_on`; v7's driver had the brief-dependency boundary (specs/20261103/06 D15) and the v8 rewrite dropped it. niko-hub batch 1: 2 of 3 dependents dead-ended at FIX. |
| D2 | Explicit paths and SELF-PICK obey D1: an explicit spec with an unsatisfied dependency is printed in Waiting with the same why (nothing runnable → today's drained report); `pickBody` offers only satisfied candidates; `picked` refuses a label whose spec waits via the existing `<spec> is not runnable — <why>` refusal. | One rule, three entry points; no override flag until someone needs one. |
| D3 | `lib/git.js` gains `commitWip(wt, message)`: `add -A -- . ':(exclude).claude/pending-question.json'`, then `commit -q --no-verify -m <message>` when anything is staged; returns the sha or `null`; a no-op (returns `null`) while `rebasing(wt)`. fanout calls it with `wip(spec): <stem>` whenever a lane becomes `stopped` (returned with `--stopped` or an unanswered pending question), `waiting`, or `dismissed` (including the automatic dismissal of a PARKED or AMENDED lane), and at `planned` on a reused worktree before the rebase. | A lane stopped at FIX held 35 staged, uncommitted files for 20+ minutes of builder work (niko-hub lane 06); nothing in the plugin may discard a build. The pending file is the relay channel, never content. |
| D4 | WIP commits never reach trunk: `run.js` COMMIT, when any commit in `merge-base(trunk, HEAD)..HEAD` has a subject starting `wip(spec):`, runs `reset -q --soft <merge-base>` before `commitAll`, so the branch carries exactly one `build(...)` commit above trunk. | Trunk history stays build + done per lane, as today; the WIP commit is a safety net, not history. |
| D5 | `prepare()` rebases a reused worktree. `worktreeAdd` reports reuse (the worktree was listed or the branch existed → `lane.reused = true`). For a reused lane whose worktree is not `rebasing`: D3's WIP commit, then `rebaseOnto(wt, trunk)`. Clean → `lane.rebased = <trunk sha>`; when a run state exists its `base` becomes that sha and its `waitingOn` is deleted. Conflict → `lane.conflicts`, `lane.conflictAt = <root HEAD>`, the rebase stays in progress and the lane's status is unchanged (its own `/spec:run` resolves it, D8). A reused lane already mid-rebase is left as it is. DISPATCH prints under the lane line `  reused worktree — rebased onto <sha>` or `  reused worktree — rebase in progress, conflicts: <files> (the lane resolves first)`. | A re-picked lane resumed on a base 4 commits behind trunk and could never progress; the hook forbids everyone but the driver from rebasing, so the driver does it. |
| D6 | `fanout.js --mark waiting --lane N --on <spec>`: accepted at WAIT for a dispatched or stopped lane and at RELAY for a stopped lane; `--on` must be a spec file under root (`rel`), else refused with `--on <spec> is not a spec file under <root>`. It runs D3's WIP commit, writes `waitingOn: <rel>` into the lane's run state (created as `{step: 'OPEN'}` when absent), `unmarkLane`, sets `lane.status = 'waiting'`, `lane.on`. `deriveWait`'s active set excludes `waiting` like `dismissed` and `merged`. RELAY prints, for every stopped lane, a first line `wait for a spec: node … --mark waiting --lane N --on <spec path>` before `answer:` and `drop it instead:`. `eligible()` treats a run state's `waitingOn` as one more D1 entry with why `waiting on <entry> (<status>, not done)`; D5 clears it. REPORT counts `, N waiting` in the outcome and warns `waiting <stem> — on <spec>; worktree kept at <wt>`. | A dependency stop had only `answered` (the same dead end) or `dismissed`; the batch's other lanes were held behind that choice. |
| D7 | `run.js --mark waiting --on <spec>`: lane only (a non-lane run is refused with `not a lane — run /spec:run <spec> first, then re-run`); accepted at BUILD, REPAIR, FIX and REVIEW; `--on` must be a spec file under root; it writes `waitingOn` into the run state, leaves `step` as it is, and prints `WAITING — <spec> waits on <on>; the lane stops here and fanout re-picks it once <on> is done on trunk`. fanout's `returned` for a lane whose run state carries `waitingOn` applies D6 without `--stopped` and without asking. | The lane agent is the one who knows the build needs another spec's surface; today it can only stop in prose. |
| D8 | `run.js` resolves a rebase at any step. At the top of `derive`, for a lane (`state.lane`) whose worktree is `rebasing`: when no conflicted file still carries markers, `add -A` and `rebase --continue` (today's MERGE_READY logic, moved); still rebasing → the step is named after `state.step` and its body is `rebaseLeft(<trunk sha>)`, which names the live trunk head; when the rebase has completed, `state.base = merge-base(trunk, HEAD)`, `state.commit = HEAD` when `state.commit` was set, and when `state.step === 'MERGE_READY'` the run goes to GATE with `review: null` and `attempts: {repair: 0, fix: 0}` — GATE is auto, so the REVIEW brief prints in the same invocation. fanout's `returned` loses its `resolving` branch (`resolving` is never written); `conflictAt` stays for the second-conflict rule. | shop-bltr's lane 08 was dispatched six times for one spec; the hand-back after a resolution only to be re-sent for GATE was two of them. The gate and review after a resolution stay: they caught a semantic conflict the textual rebase missed. |
| D9 | WAIT lands merge-ready lanes early. `deriveWait`, when not every active lane is done or stopped: if some lane is `done`, no lane is `sent-back`, and no dispatched lane's worktree is `rebasing`, it auto-runs `mergeLane` on the first `done` lane (batch order), which may leave the lane `merged`, `sent-back` (WAIT already prints the re-dispatch) or the batch at MERGE_RED. The `returned` mark of a MERGE_READY lane therefore lands it in the same process. MERGE keeps its loop for whatever is left. | Trunk sat idle 15 minutes with two merge-ready lanes behind the slowest lane; landing early also shrinks the window in which a later lane's rebase conflicts. |
| D10 | Spec edits are refused by the driver. `gateStep`, after a green gate: `specEdits` = every file changed since `base` matching `specs/**/*.md` other than the lane's own spec and its `.run/`, plus the own spec when its `## Decisions` section text differs from base. Non-empty → ESCALATE with `why: 'spec-edit'`, question `<id> edited spec text it may not: <list>. How should it continue?`, options `revert` (the driver runs `checkout <base> -- <files>`, re-writes the own spec's status line, and returns to GATE) and `amend` (today's: spec to draft). `escalate` accepts `revert` only for `why: 'spec-edit'`. An edit to the own spec outside Decisions (an AC correction in a FIX round) still passes as today. | Two lanes in two repos rewrote or dropped locked Decisions and merged; doctrine says the user edits specs. A script check beats a reviewer's judgment. |
| D11 | `run.js --mark unmet --decision <id> --why <text>`: accepted at BUILD, REPAIR, FIX and REVIEW; `--decision` must match a row id of the spec's Decisions table, else refused with the known ids. It goes to ESCALATE with `why: 'decision'`, `from: <step>`, question `<spec id> cannot meet <decision id>: <text>. How should it continue?`, options `retry` (back to `from` on opus with fresh attempts), `park` (today's), `amend` (description `set the spec to draft; proposed amendment: <text>`). In a lane this is a pending question (today's `ask`), relayed by fanout. `rebaseLeft` says it too: a resolution that cannot keep a Decision marks `unmet`, it does not decide. | shop-bltr's lane 08 dropped two Decisions as superseded by the lane merged before it, with no reviewer yet; niko-hub's lane 04 amended two and edited a draft spec. |
| D12 | Reports tell the truth after a rebase: `run.js` re-renders the MERGE_READY report with the current head when D8 completes a rebase; `mergeLane` records `lane.landed = <trunk sha after the fast-forward>` and REPORT prints `merged <stem> as <sha> into trunk; queue item ticked`. | Both pilots saw the pre-rebase hash printed after a resolved conflict. |
| D13 | Prose: `fanout.md` — WAIT lands MERGE_READY lanes as they return, names `waiting --lane N --on <spec>`, says a conflict is resolved, gated and reviewed inside the lane's own dispatch, and the Long-marks note becomes "every `returned` of a MERGE_READY lane may run a rebase, fast-forward and trunk gate: 600000 ms". `run.md` — lane bullets for `waiting --on`, `unmet`, and "a lane never edits its spec's Decisions or any other spec". `doctrine.md` § When to ask gains one sentence: a lane never edits a spec; an unmet Decision is a question. `builder.md` gains "Never edit the spec or any other spec file; a Decision you cannot honour goes in your reply." `reviewer.md` gains "A changed Decisions row or another spec file in the diff is blocking." `docs/v8/architecture.md` fanout and run notes gain `waitingOn`, the rebase guard, WIP folding and early landing. `docs/v8/interface-contract.md`: `/spec:fanout` arguments `[--pick] [<spec path>…]`; the fanout row's marks are exactly `planned`, `picked --label <title>…`, `dispatched`, `returned --lane <id> [--stopped "<reason>"]`, `resent`, `answered --lane <id> [--label <label>]`, `resumed`, `dismissed --lane <id>`, `waiting --lane <id> --on <spec>`, `gate-repaired`, `reported`; the run row gains `waiting --on <spec>`, `unmet --decision <id> --why <text>` and `escalate <retry\|park\|amend\|revert>`; the fanout ask row names the dependency stop; `--batch`, `--include-fixes`, `--override-serial`, `--ask` and `merged` are gone. | The contract listed four flags and a mark that do not exist; the pilots read it. |
| D14 | Tests pin every criterion by execution in `tests/fanout.test.js`, `tests/run.test.js` and `tests/git.test.js` on tmp hosts (today's fixtures: `host()`, `finish()`, `fixture()`), including one contract-doc grep; existing tests are kept, and the rebase-conflict test moves from the resend path to D8's one-dispatch path. | The suite is the gate; a behaviour that is not pinned drifts (this brief is a list of drifts). |

## Acceptance Criteria

- **AC-20261105-02-1**: WHEN the queue holds hardened A, hardened B with `depends_on: [<A path>]` and hardened C with `depends_on: [<D path>]` where D is `draft`, and `lanes` is 4 THE SYSTEM SHALL auto-pick A alone and print under Waiting `<B path> waits — depends on <A path> (lane 1 this batch)` and `<C path> waits — depends on <D path> (draft — it cannot land in this fan-out)`; AND WHEN A has merged and `reported` is marked THE SYSTEM SHALL auto-pick B in the next PLAN.
- **AC-20261105-02-2**: WHEN a hardened spec's `depends_on` names a path with no file on disk, or a spec whose root copy is `done` THE SYSTEM SHALL pick it as if `depends_on` were empty; WHEN it names a hardened spec that is not picked in this walk THE SYSTEM SHALL print `depends on <path> (hardened, not done)`.
- **AC-20261105-02-3**: WHEN `fanout.js <B path>` is run with B's dependency A not done THE SYSTEM SHALL print B in Waiting with the D1 reason and no lane; WHEN `--pick` is run THE SYSTEM SHALL offer A and not B; WHEN `picked --label <B's title>` is marked THE SYSTEM SHALL refuse with `<B path> is not runnable — depends on <A path> (hardened, not done)`.
- **AC-20261105-02-4**: WHEN a dispatched lane's worktree holds a staged file, an untracked file and `.claude/pending-question.json`, and `returned --lane N --stopped "x"` is marked THE SYSTEM SHALL leave the lane branch one commit ahead with subject `wip(spec): <stem>` containing both files and not the pending file, and a clean worktree; AND WHEN `dismissed --lane N` follows THE SYSTEM SHALL keep that commit and the worktree.
- **AC-20261105-02-5**: WHEN a lane's branch carries a `wip(spec): <stem>` commit and `run.js` reaches COMMIT THE SYSTEM SHALL leave exactly one commit between `merge-base(trunk, HEAD)` and HEAD, with a `build(` subject and no `wip(spec):` subject on the branch.
- **AC-20261105-02-6**: WHEN PLAN picks a spec whose worktree and branch exist two commits behind trunk with a run state at FIX and uncommitted edits, and `planned` is marked THE SYSTEM SHALL print under that lane `reused worktree — rebased onto <trunk sha>`, leave the branch rebased on trunk with the edits in a `wip(spec):` commit, and set the run state's `base` to the trunk sha.
- **AC-20261105-02-7**: WHEN the rebase of AC-6 conflicts THE SYSTEM SHALL print `reused worktree — rebase in progress, conflicts: <files> (the lane resolves first)`, leave the rebase in progress; AND WHEN `run.js` is run in that lane THE SYSTEM SHALL print a step named `FIX` whose body is the resolve text naming the trunk sha; AND WHEN the markers are gone and `run.js` is re-run THE SYSTEM SHALL continue the rebase, set `base` to `merge-base(trunk, HEAD)`, and print the FIX brief.
- **AC-20261105-02-8**: WHEN a lane at FIX marks `waiting --on <X path>` THE SYSTEM SHALL write `waitingOn` into the run state, keep `step` FIX, and print a line starting `WAITING — `; WHEN a non-lane run marks it THE SYSTEM SHALL refuse with exit 2 naming `/spec:run <X path>`.
- **AC-20261105-02-9**: WHEN fanout marks `returned --lane N` for a lane whose run state carries `waitingOn` THE SYSTEM SHALL set the lane `waiting` with a `wip(spec):` commit and no lane marker, land the batch's other done lanes without that lane, print `waiting <stem> — on <X path>` in REPORT, and in the next PLAN print `<spec> waits — waiting on <X path> (hardened, not done)`; AND WHEN X is `done` on trunk THE SYSTEM SHALL pick it, rebase its worktree and remove `waitingOn`.
- **AC-20261105-02-10**: WHEN `waiting --lane N --on <spec>` is marked at WAIT for a dispatched lane, or at RELAY for a stopped lane THE SYSTEM SHALL accept it with the AC-9 effects; WHEN `--on` is not a spec file under root THE SYSTEM SHALL refuse with exit 2.
- **AC-20261105-02-11**: WHEN two lanes are dispatched and lane 2 returns MERGE_READY while lane 1 is still out THE SYSTEM SHALL, inside the `returned --lane 2` mark, rebase, fast-forward trunk, gate, tick the queue and remove lane 2's worktree, leaving WAIT listing lane 1; WHEN instead lane 1 is `sent-back` with a rebase in progress THE SYSTEM SHALL leave lane 2 `done` until lane 1 lands.
- **AC-20261105-02-12**: WHEN a lane's rebase onto trunk conflicts at landing and its agent resolves the files and re-runs `run.js` THE SYSTEM SHALL, in that one invocation, continue the rebase, set `base` to `merge-base(trunk, HEAD)`, run GATE and print the REVIEW brief; AND WHEN the lane then reaches MERGE_READY and `returned` is marked THE SYSTEM SHALL land it without a second re-dispatch, with no `resolving` key in the fanout state.
- **AC-20261105-02-13**: WHEN a build changes another spec file, or a row of its own spec's Decisions table THE SYSTEM SHALL go to ESCALATE after the green gate with a question listing those files and options `revert` and `amend`; WHEN `escalate revert` is marked THE SYSTEM SHALL restore those files from `base`, keep the own spec's status line, and return to GATE; WHEN only an acceptance-criterion line of the own spec changed THE SYSTEM SHALL proceed to REVIEW as today.
- **AC-20261105-02-14**: WHEN a lane at FIX marks `unmet --decision D1 --why "trunk removed the hook"` THE SYSTEM SHALL write a pending question whose text contains `cannot meet D1: trunk removed the hook` with options `retry`, `park`, `amend` (the amend description containing the text) and stop; WHEN `--decision D9` names no row THE SYSTEM SHALL refuse naming the known ids; WHEN the answer is `retry` THE SYSTEM SHALL return to FIX with fresh attempts on opus.
- **AC-20261105-02-15**: WHEN a lane's rebase completes after a conflict THE SYSTEM SHALL print `commit <current head>` in the MERGE_READY report, and REPORT SHALL print `merged <stem> as <sha>` where `<sha>` is trunk's head after that lane landed.
- **AC-20261105-02-16**: WHEN `docs/v8/interface-contract.md` is read THE SYSTEM SHALL contain the fanout marks list of D13 and no `--batch`, `--include-fixes`, `--override-serial`, `--ask <key` or a bare `merged` mark in the fanout rows, and `[--pick] [<spec path>…]` as `/spec:fanout`'s arguments.

## Assumptions

- A1: This is a behaviour change with no ADR added or overturned, so `architecture: false` and no `--confirmed` lock — if false: set `architecture: true`, re-lock with `--confirmed` after JJ's yes.
- A2: Explicit spec paths get no override of the dependency rule (D2) — if false: a `--force` flag skips D1 for explicit paths only.

- A5: A lane may mark `waiting --on` a spec that is already `done` (its base predates it); fanout's next PLAN re-picks and rebases it — if false: run.js refuses with "already on trunk" and the orchestrator marks `dismissed` and re-picks by hand.

- A8: The two-dispatch resend path (`resolving`) is deleted rather than kept as a fallback (D8) — if false: keep `resent` as the recovery when a lane returns with a rebase completed outside run.js.
