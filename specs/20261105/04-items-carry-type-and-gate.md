# Items carry type and gate

## Intent
- You asked: `/spec:status` (and the bash `spec-status`) must have exactly v7's behaviour and UI/UX, built cleanly on v8's architecture — not v7's code copied in — with the two `📈` lines and the "done since last release / never released" footer clause absent. This spec is the engine half: the state v7's screen reads and v8 does not hold yet.
- I will build:
  - Queue items gain `type` (prompt items: `plan | prototype | fix | decide`) and `after` (`{brief: "NN"}` or `{spec: "specs/…md"}`); `queue add` takes `--type` and `--after`; the paste line is v7's `promptAction`; `queue next` and `list` honour the gate.
  - `lib/work.js`: the one reader of specs and roadmap briefs with v7's rules — brief ids normalised, `Depends on:` items parsed strictly, both `Superseded by` banner forms, v7's brief state words (`unplanned | in-flight | done | superseded`), a brief done when its live specs are done.
  - `lib/state.js`: `liveRun` reads a run sidecar in the root or in the spec's lane worktree, so a spec being built counts as `implementing`; bracketless `depends_on: a.md, b.md` splits like the bracketed form.
  - `queue.js reconcile` ticks a brief item once its brief is done and a spec item once its spec is done or superseded and not live; `fanout.js eligible()` waits a candidate whose queue item has an unmet `after`.
  - `migrate.js` carries `lane → type` and `after` from a v1 queue and fills them on an already-migrated host from the newest `spec-v7-backup`, printing each fill; idempotent.
  - Tests by execution for every criterion; `spec/commands/queue.md`, `docs/v8/interface-contract.md` §7 and `docs/v8/architecture.md` §2/§9 reconciled.
- I will not touch:
  - `run.js`, worktrees, sidecar writes, fanout's lane mechanics beyond the one `after` clause, the queue file's location and the verbs other than `add`; no `origin`, no `when`, no ledger.
  - `status.js` and its render: spec 05 owns the screen. `doctor.js` is unchanged.
  - `~/projects/niko-hub` and `~/projects/shop-bltr`: the migration plan is printed there, never applied by the build.
  - The plugin version (ADR-0039 D4: bumped at release).
- Architecture or behaviour change: yes — the queue model gains `type` and `after`, brief doneness is v7's rule (specs/20261105/01 D2 retired), a lane-worktree sidecar makes a spec implementing, and fanout honours the gate. ADR-0041 records it. JJ said yes on 2026-11-05 in the main session, covering both this spec and spec 05 and their locks.

## Goal

After this spec a session can `queue add "fix the login bug"` and `queue next` prints `/spec:plan fix the login bug`; an item added with `--after 03` is skipped by `next` and shown by `list` with `⏳ after brief 03` until brief 03's specs are all done, and fanout never starts a spec whose item is gated. On niko-hub `migrate.js` (plan only) lists the 5 `type` and 13 `after` fills v7's backup holds, so once JJ applies it the queue carries exactly what v7's screen showed. Spec 05 then renders that state as v7's screen.

## Decisions

| ID | Decision | Why |
|----|----------|-----|
| D1 | Queue item shape (ADR-0041 §1): `{id, kind, payload, added, done?, type?, after?}`. `type` only on `kind: prompt`, one of `plan`, `prototype`, `fix`, `decide`; `after` is `{brief: "NN"}` (normalised: zero-padded to two digits, suffix lowercase: `3` → `03`, `4B` → `04b`) or `{spec: "specs/…md"}` (root-relative, `@`/`./` stripped). No `origin`, no `when`. `lib/state.js readQueue` keeps passing the file through; nothing validates on read. | The screen needs exactly the two fields v7's niko-hub items carried: the paste's command and the gate. |
| D2 | `queue add <payload> [--top] [--type <t>] [--after <NN\|roadmap path\|spec path>]`. Type default for a prose payload: `plan`; a payload starting `/spec:fix `, `/spec:plan ` or `/spec:prototype ` gets that type; `--type` overrides; `--type` with a spec or brief payload, or a value outside the four, is refused (exit 2, `queue: --type takes plan, prototype, fix or decide, on a prompt item`). `--after`: a brief id or roadmap path needs a `docs/roadmap/NN-*.md` (stored `{brief}`); a `.md` path under `specs/` needs the file (stored `{spec}`); anything else is refused exit 2 naming the target (`queue: --after target not found: <as typed>`). `--after` is accepted on every kind. | One write path; a new prose item is paste-ready; a gate on a missing target would never open. |
| D3 | `pasteLine(root, item)` for a prompt item is v7's `promptAction`: `/spec:plan <payload>`, `/spec:prototype <payload>`, `/spec:fix <payload>` for the three command types unless the payload already starts with that command (then verbatim); `📌 decide: <payload>` for `decide`; the payload verbatim with no type. Spec and brief items paste as today. `queue next` prints it; `next --json` keeps `paste`. | niko-hub's q37 (no type) must print verbatim, q70 (`plan`) with its command, exactly as v7 did. |
| D4 | `lib/work.js` (new, ≤250 LOC, no CLI): `normBrief(v)` (D1's normalisation; `04-auth` → `04`; a non-id string returned trimmed), `briefOrd(num)` (`04 < 04a < 04b < 05`), `readSpecs(root)` and `readBriefs(root, specs)`. `readSpecs` walks `specs/**/*.md` in lexical order skipping `*.run` dirs, reads frontmatter through `state.readSpec`, skips a file with no `status:`, and returns `{path, status, brief (normBrief or null for n/a, none, -, —, absent), depends_on (array, each `@`/`./` stripped), superseded_by, filePlan, filePaths}` with `status` from D6's `specState`. `readBriefs` reads `docs/roadmap/` files matching `/^(\d+[A-Za-z]?)-(.+)\.md$/` except `00-overview.md`, sorted by filename; per brief: `num = normBrief(id)`, `name`, `file`, `phase` = `Phase: (P\d+)` in the head (the text before the first `\n## `, HTML comments removed, whitespace flattened), `depends_on` = the `Depends on:` value cut at `·`, at the next `Word:` label or end, split on commas outside parentheses, each item accepted only when it is an exact brief id (`NN`, `NNa`, optional `brief ` prefix, optional `-name` suffix, optional trailing parenthetical) and normalised, `none`-spellings dropped, everything else kept in `dep_rejects`; `superseded` = `/^>\s*(\*\*)?Superseded by\b/m`; `specs` = the live (not superseded) specs whose `brief` equals `num`; `status` = `superseded` when the banner is set and every member is done, else `unplanned` with no members, `done` when every member is done, else `in-flight`. | One parser for roadmap headers and one brief state, shared by queue.js (D5) and spec 05's screen; niko-hub's `02-B (02a-2; parts of 02a-3a)` is brief 02 and never `3a`. |
| D5 | `queue.js reconcile(root, q)`: as today, plus a pending `brief` item is ticked (`done: <now>`, written on the next write) when `readBriefs` says its brief is `done`; a pending `spec` item is ticked when its spec's frontmatter is `done` or `superseded` and `liveRun` finds no live sidecar. Readiness: `ready(item)` is true without `after`; with `{brief}` when that brief's status is `done`; with `{spec}` when that spec's status is `done` or `superseded`; a target with no file or no brief is never ready. `next` prints the paste of the first pending ready item; with pending items and none ready it prints `nothing ready — N waiting on after gates` exit 0 (`--json`: `{empty: false, waiting: N}`); `list` ends an unready row with two spaces and `⏳ after brief NN` or `⏳ after <spec stem>` (basename without `.md`); `list --json` items carry `type` and `after` as stored. `fanout.js tickQueue` and `move`/`done`/`show` are unchanged. | v7 retired a brief item with its brief; a half-open screen that says done while the queue still pastes `/spec:plan` for it would lie. |
| D6 | `lib/state.js`: `liveRun(root, rel)` returns the parsed sidecar when one is live at `<root>/<rel minus .md>.run/state.json` or `<root>/.claude/worktrees/spec-<stem>/<rel minus .md>.run/state.json`, else `null`; live = parses, `ended !== true`, `step` not `DONE`, `PARKED` or `AMENDED`. `specState(root, rel, status)` = `implementing` when `liveRun` is non-null and `status` is neither `done` nor `superseded`, else `status`. The worktree's own frontmatter is never read. `reconcile`'s in-flight check uses `liveRun`. | v8 runs in a worktree and leaves main's frontmatter at `hardened`; v7 wrote `implementing` into the file. The screen must say what is being built, and the queue must not tick a spec still in a lane. |
| D7 | `parseFrontmatter`: an unbracketed `depends_on: a.md, b.md` yields `['a.md', 'b.md']`; a single value stays a one-element array for `depends_on` only. Consumers (`fanout.js eligible()` under spec 02 D1, `readSpecs`) see the split. | niko-hub's specs carry the bracketless form; fanout under spec 02 would otherwise see one nonsense entry. |
| D8 | `fanout.js eligible()`: after spec 02's dependency walk, a candidate whose pending queue item carries an unmet `after` (D5's `ready`) goes to `waited` with why `after brief NN (<brief status>)` or `after <spec path> (<spec status>\|missing)` — v7's blocker words. Explicit paths and `--pick` obey it through the same walk. | A fan-out that started a spec the screen shows under `⛔ … ⏳ after brief 03` would make the screen lie. |
| D9 | `migrate.js convertQueue` carries `lane` → `type` (only the four values; any other `lane` dropped) and `after` (`{brief}` normalised by D1, `{spec}` as written). New op `queue-fields <path> (N fills)`: when the queue is already v2 and a `<git-common-dir>/spec-v7-backup/*/spec-queue.json` exists, the source is the newest backup (lexically last directory) whose items carry any `lane` or `after`; for each v2 item with a same-id source item, a `type` or `after` the v2 item lacks is one fill, listed as `qNN type plan` / `qNN after brief 03` / `qNN after specs/…md`; `--apply` writes them through `writeQueue`; a second run plans nothing; no backup or no fills → no op. The existing dirty-tree refusal and backup step apply as today. | niko-hub and shop-bltr were migrated before these fields existed; the backup is the only copy. |
| D10 | Docs: `spec/commands/queue.md` names `add [--top] [--type plan\|prototype\|fix\|decide] [--after <NN\|spec>]` and the `⏳ after` row; `docs/v8/interface-contract.md` §7 states the D1 item shape, the `add` flags, D3's paste lines and D5's readiness (the v7 `lane`/`when`/`origin`/`trigger` fields are struck); `docs/v8/architecture.md` §2 item shape line, §9 `queue.js` note (`≤ 200 LOC`) and a `lib/work.js` bullet under the libs section. | The contract is the promise. |
| D11 | Tests by execution on tmp hosts (today's helpers): `tests/queue.test.js` (D2, D3, D5), `tests/state.test.js` (D6, D7), `tests/fanout.test.js` (D8), `tests/migrate.test.js` (D9, synthetic backup), a new `tests/work.test.js` (D4 on a roadmap with every header shape), plus the two manual read-only checks of AC-10 recorded in the close commit message. | The suite is the gate; the real hosts are the reason the fields exist. |

## Acceptance Criteria

- **AC-20261105-04-1**: WHEN `queue add "fix the login bug"` runs THE SYSTEM SHALL store `type: "plan"` and `queue next` SHALL print `/spec:plan fix the login bug`; WHEN the payload is `/spec:fix specs/x.md — gate red` THE SYSTEM SHALL store `type: "fix"` and `next` SHALL print the payload verbatim; WHEN `--type decide` is given THE SYSTEM SHALL print `📌 decide: <payload>`; WHEN `--type prototype` is given with a prose payload THE SYSTEM SHALL print `/spec:prototype <payload>`.
- **AC-20261105-04-2**: WHEN `--type plan` accompanies a spec path or a brief id, or `--type other` is given THE SYSTEM SHALL exit 2 naming the four types and store nothing; WHEN a prompt item has no `type` (a migrated item) THE SYSTEM SHALL print its payload verbatim.
- **AC-20261105-04-3**: WHEN `queue add "x" --after 3` runs with `docs/roadmap/03-rounds.md` present THE SYSTEM SHALL store `after: {brief: "03"}`; WHEN `--after docs/roadmap/04B-boards.md` THE SYSTEM SHALL store `{brief: "04b"}`; WHEN `--after @specs/20261104/01-a.md` THE SYSTEM SHALL store `{spec: "specs/20261104/01-a.md"}`; WHEN the target has no file THE SYSTEM SHALL exit 2 naming it as typed.
- **AC-20261105-04-4**: WHEN the queue head is gated by `after: {brief: "03"}` and brief 03 has no spec THE SYSTEM SHALL make `queue next` print the next ready item's paste and `queue list` end that row with `  ⏳ after brief 03`; WHEN every pending item is gated THE SYSTEM SHALL print `nothing ready — N waiting on after gates` with exit 0; WHEN the gate names `specs/20261102/08-server-timeouts.md` THE SYSTEM SHALL end the row with `⏳ after 08-server-timeouts`; WHEN every live spec of brief 03 is `done` THE SYSTEM SHALL print the gated item from `next`.
- **AC-20261105-04-5**: WHEN a spec item's `after` names a spec whose status is `superseded` THE SYSTEM SHALL treat the gate as met; WHEN it names a path with no file THE SYSTEM SHALL never treat it as met.
- **AC-20261105-04-6**: WHEN a roadmap brief has one `done` spec and one `superseded` spec and its brief item is pending THE SYSTEM SHALL tick that item on the next queue write (`list` no longer shows it, `--json` carries `done`); WHEN the brief has a `done` and a `hardened` spec THE SYSTEM SHALL leave the item pending; WHEN a spec item's spec is `done` in frontmatter but `.claude/worktrees/spec-<stem>/<spec>.run/state.json` holds `{"step": "GATE"}` THE SYSTEM SHALL leave the item pending; WHEN that sidecar holds `{"step": "DONE", "ended": true}` THE SYSTEM SHALL tick it.
- **AC-20261105-04-7**: WHEN `readBriefs` reads a head `Phase: P1 · Depends on: 02 (02a-2; parts of 02a-3a), brief 04-auth, 05B, none, 2026-style <!-- x -->` wrapped over two lines before the first `##` THE SYSTEM SHALL return `depends_on: ["02", "04", "05b"]`, `dep_rejects: ["2026-style"]` and `phase: "P1"`; WHEN the file is `04A-boards.md` THE SYSTEM SHALL return `num: "04a"`; WHEN a brief body holds `> Superseded by 04` or `> **Superseded by 04**` and every member spec is done THE SYSTEM SHALL return `status: "superseded"`; WHEN its members are a done spec and a hardened spec THE SYSTEM SHALL return `in-flight`; WHEN it has no live member THE SYSTEM SHALL return `unplanned`; WHEN a spec stamps `brief: 4B` THE SYSTEM SHALL count it a member of `04b`; WHEN a spec file has no `status:` line THE SYSTEM SHALL omit it from `readSpecs`.
- **AC-20261105-04-8**: WHEN a spec's frontmatter says `hardened` and `.claude/worktrees/spec-<stem>/<spec>.run/state.json` holds `{"step": "BUILD"}` THE SYSTEM SHALL report `specState` as `implementing`; WHEN the sidecar holds `{"step": "PARKED", "ended": true}` or `{"step": "AMENDED"}`, or the frontmatter says `done` or `superseded` THE SYSTEM SHALL return the frontmatter status; WHEN the live sidecar sits at `<root>/<spec>.run/state.json` THE SYSTEM SHALL read it the same way; WHEN the worktree's copy of the spec says `done` and the sidecar is live THE SYSTEM SHALL still return `implementing`.
- **AC-20261105-04-9**: WHEN a spec's frontmatter reads `depends_on: specs/a.md, specs/b.md` THE SYSTEM SHALL parse two entries, and `fanout.js` PLAN SHALL evaluate both under spec 02 D1; WHEN the queue holds a hardened spec item with `after: {brief: "03"}` and brief 03 is `unplanned` THE SYSTEM SHALL print under Waiting `<spec> waits — after brief 03 (unplanned)` and pick no lane for it; WHEN brief 03 is `done` THE SYSTEM SHALL pick it; WHEN the same spec is passed as an explicit path THE SYSTEM SHALL print the same Waiting line.
- **AC-20261105-04-10**: WHEN `migrate.js` plans a v1 queue whose items carry `lane: "plan"` and `after: {brief: "3"}` THE SYSTEM SHALL write v2 items with `type: "plan"` and `after: {brief: "03"}`; WHEN it plans a v2 queue beside `<git-common-dir>/spec-v7-backup/<ISO>/spec-queue.json` whose same-id items carry those fields THE SYSTEM SHALL list `queue-fields` with one line per fill, write them on `--apply`, and plan no `queue-fields` on a second run; WHEN no backup exists, or the backup holds no `lane`/`after`, THE SYSTEM SHALL plan no `queue-fields` op; WHEN run read-only (no `--apply`) on `~/projects/niko-hub` THE SYSTEM SHALL list 5 `type plan` fills (q70, q94, q95, q111, q113) and 13 `after` fills (q37 02b, q70 02b, q89 03, q90 03, q94 03, q95 04, q104 03, q105 04, q106 06, q108 spec 08-server-timeouts…, q110 03, q111 03, q113 15), and on `~/projects/shop-bltr` the fills for q49, q50 and q52 that its backup holds — both listings recorded in the close commit message; the apply on either host is JJ's to run.
