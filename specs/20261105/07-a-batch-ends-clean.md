# A batch ends clean

## Intent
- You asked: plan roadmap 36 — the fan-out trial's third-round findings: a batch ends the turn instead of looping into a full context, parked lanes' fixes run as lanes, trunk never goes red from a rebase onto a moved trunk, a dismissed lane can be discarded, a mark re-run after a refused step is not an error, reports and the contract tell the truth, and evidence ACs have a channel.
- I will build:
  - REPORT ends the turn: after `reported` the driver prints how many specs and fixes are left with the `/clear` line, and fanout.md says the orchestrator stops there; the next bare run plans.
  - A `/spec:fix <spec> — <symptom>` queue item (the one a parked lane writes) is a fix lane: `run.js` gains a lane-only `--fix "<symptom>"` mode whose builder brief is the symptom, whose commit is `fix(<id>): <symptom>`, and whose landing ticks the prompt item; PLAN picks it after the spec's own lane is no longer live.
  - At landing, a lane whose base is older than trunk is gated on the rebased tree before the fast-forward; red sends it back to its own `/spec:run` at GATE with the first failing line. MERGE_RED prints the first failing line and says a flaky re-run needs no commit.
  - `dismissed --lane N --discard` removes the worktree and branch after the WIP commit and prints the sha; `dismissed` is accepted at DISPATCH, MERGE_RED and REPORT.
  - `lib/driver.js` treats a mark whose effect is already in the state as applied: checkpoint, exit 0.
  - fanout refuses with the newest backup as the remedy when lane markers exist but `spec-fanout.json` is missing; the dismissed and WAIT lines say what trunk has and that a lane at ESCALATE holds a question.
  - `run.js` appends `<spec>.run/evidence.md` to the build commit body; plan.md and builder.md say evidence goes there.
  - docs/v8/interface-contract.md lists the marks, flags and queue subcommands the code accepts; queue.js refuses a trailing `--type` or `--after` with no value.
- I will not touch:
  - Load, gate concurrency and the host environment (brief 37); anything that asks the user more (brief 35).
  - The non-lane `/spec:fix` (fix.md stays in-session prose; brief 33's fix driver is not this spec).
  - `block-worker-git.sh`; the queue data model (spec 04's `type`/`after` stay); File Plan overlap order (specs/20261103/15 D1); the plugin version (ADR-0039 D4).
- Architecture or behaviour change: no — the fan-out and run drivers' behaviour changes exactly as brief 36 specifies; no ADR is added or overturned (ADR-0039 D1 names the fix lane, D4 keeps the bump at release).

## Goal

A fan-out batch starts with a fresh orchestrator, lands only green work on trunk, drains the fixes its own lanes created, discards on request, never turns a successful merge into exit 2, and tells the truth in every line. On the trial this would have saved shop-bltr's five-hour single-session drain, niko-hub's seven minutes of a type error on main plus a hand repair, two "queue drained" lies over running lanes, and two unmeetable evidence criteria.

## Decisions

| ID | Decision | Why |
|----|----------|-----|
| D1 | REPORT ends the turn. `deriveReport` computes `left = plan(root, config).picked` as before but counts it by kind: `next` becomes `N spec(s) and M fix(es) left — /clear, then /spec:fanout to continue` when anything is left, else `nothing needs you — queue drained`. The `reported` mark keeps returning `{step: 'PLAN'}`; the driver prints its checkpoint and stops (PLAN has a mark, so the frame does not render it). fanout.md's REPORT bullet becomes: mark `reported`, then end the turn and report; the user runs `/spec:fanout` again, after `/clear`; never loop to the next batch in the same turn. | shop-bltr ran three batches, twelve specs and five hours in one session; every lane's return sat in that context. The `/clear` line after a checkpoint is already the doctrine's resume point. |
| D2 | Fixes are lanes. `candidates()` also takes pending queue items of `kind: 'prompt'`, `type: 'fix'`, whose payload matches `^/spec:fix (specs/\S+\.md)(?: — (.+))?$`; the spec must exist on disk, else the item waits with why `fix item names no spec on disk`. A fix candidate is runnable when its origin spec is not in a live lane (`pending.isLane(<spec worktree>)` false; an ENDED run state is fine) and its own `after` gate is met; it is ordered after any runnable spec candidate in the same walk. A fix lane is `{kind: 'fix', spec, symptom, item: <queue id>, stem: 'fix-<spec stem>', worktree: '.claude/worktrees/fix-<spec stem>', branch: 'fix/<spec stem>'}`; its Agent prompt is `/spec:run <spec> --root <wt> --fix <symptom>`. `finalize` for a fix lane ticks the prompt item by id, flips no spec status and makes no `chore(spec): … done` commit. The interface contract's `--include-fixes` is gone; the behaviour is the default. | A parked lane queues `/spec:fix <spec> — <first red line>` and nothing drained it; the pilots ran them by hand. ADR-0039 D1 names the fix lane as the path for a small repair. |
| D3 | `run.js --fix "<symptom>"` is a lane-only mode (refused otherwise with `--fix runs only as a fanout lane — use /spec:fix here`). OPEN accepts a `done` or `hardened` spec, writes no status into the spec, and records `fix: <symptom>` in the run state; the BUILD brief replaces the Intent with `## Fix\n<symptom>` plus `Reproduce it, write a regression test that fails for that reason, fix the cause.`, prints the spec's Decisions and ACs as today and no File Plan; the reviewer brief carries the same `## Fix` block; `specEdits` (spec 02 D10) applies unchanged; COMMIT's message is `fix(<spec id>): <symptom>`; MERGE_READY as today. GATE, REPAIR, REVIEW, FIX, ESCALATE, WIP folding and the rebase guard are reused as they are. | Reusing run.js keeps one driver and one hook contract; a second fix driver is brief 33's, not this spec's. |
| D4 | Trunk never goes red from a moved base. In `mergeLane`, after a clean `rebaseOnto`, when the lane's pre-rebase base (`merge-base(trunk, HEAD)` read before the rebase) differs from trunk's head, the driver runs `host.gate(wt, config)` in the lane worktree before the bookkeeping commit. Green → as today. Red → the lane becomes `sent-back` with `lane.red = redLine(tail)` (the helper moves to `lib/host.js` as `firstRedLine`), its run state is rewritten to `{...run, step: 'GATE', base: <new merge-base>, review: null, attempts: {repair: 0, fix: 0}}`, and the WAIT/MERGE re-dispatch body prints `lane N gate red after rebase: <line>` under its Agent line; the lane's own `/spec:run` then gates, repairs, reviews and returns MERGE_READY. A lane whose base already is trunk's head lands as today; `gateAfter` on trunk stays (a cache hit for an unchanged tree) and MERGE_RED keeps meaning trunk itself is red. | niko-hub's lane 06 rebased textually clean over lane 10's harness tightening and put a type error on main for seven minutes; the repair was a hand commit on trunk. One extra gate per moved-trunk landing is cheaper than that. |
| D5 | MERGE_RED tells the failing line. `deriveRed`'s body opens with `first failing line: <firstRedLine(tail)>`, then the last 15 lines of the tail, then: `Repair it in <root> (dispatch a builder or fix it here) and commit the repair, or re-run as it is when the failure was a flake: mark gate-repaired either way; the driver re-runs the gate.` `gate-repaired` keeps refusing uncommitted tracked changes. | The turbo output buried one TypeScript error under thirty task lines, and the text implied a commit was required for a flaky re-run. |
| D6 | Dismiss can discard. `dismissed --lane N [--discard]`: after today's WIP commit, with `--discard` the driver records `lane.wip = <sha or null>`, runs `git.worktreeRemove(root, lane.worktree, {deleteBranch: lane.branch, force: true})`, sets `lane.discarded = true`; the checkpoint's `after` line prints `discarded lane N — wip <sha>, recoverable for a day via git reflog`. Without `--discard`, as today. `dismissed` is accepted at DISPATCH (a `planned` lane whose worktree may not exist yet: it is skipped by `prepare` and dispatch), MERGE_RED and REPORT. | The pilot could not delete a stopped lane's work: dismissed keeps everything and the hook blocks a manual removal while any lane is open. |
| D7 | A mark that already happened is not an error. `makeDriver` takes an optional `applied(verb, state, flags, ctx) → boolean`. When the settled step refuses the verb and `applied` returns true, the frame prints `✅ checkpoint — <loaded step> → <settled step>; mark <verb> was already applied; safe to /clear …` and exits 0, running no step. fanout's `applied`: `returned`/`dismissed`/`waiting` when the named lane's status is no longer `dispatched` (or is already that status); `planned`/`picked` when `step !== 'PLAN'`; `dispatched` when no lane is `planned`; `resent` when no lane is `sent-back`; `resumed` when no lane is `answered`; `gate-repaired` when `!state.red`; `reported` when `step === 'PLAN'`. | A `returned` refused by a dirty tree had already recorded the lane as done; the re-run merged inside `settle` and then printed "not accepted at REPORT", exit 2, so a successful merge read as a failure. |
| D8 | A missing state file is named, not hidden. fanout's `load`, when `readFanout` is null and any `<common>/worktrees/*/spec-lane-open` with owner `fanout` exists, refuses: `lanes are open (<worktree names>) but <fanout path> is missing — restore it: cp <newest spec-v7-backup/*/spec-fanout.json> <fanout path>, then re-run` (when no backup exists: `… — reconstruct it, or remove the markers to abandon the lanes`). | A migrate wipe left two running lanes reported as "queue drained" on both hosts. |
| D9 | Reports say what trunk has. REPORT's dismissed line is `dismissed <stem> — worktree kept at <wt>, spec left hardened in the lane` plus ` (trunk: <status>)` when the root copy's status is not `hardened`; a discarded lane prints `dismissed <stem> — worktree and branch removed (wip <sha>)`. WAIT's lane list appends ` (question waiting — mark returned)` to a dispatched lane whose pending question is unanswered. Merged lines keep spec 02's `as <sha>`. | The pilot read "spec back to hardened" for a spec that was superseded on main; a lane at ESCALATE was listed with no hint that the orchestrator had to act. |
| D10 | Evidence has a channel. `run.js` COMMIT reads `runFile(ctx, 'evidence.md')`; when present and non-blank its text is appended to the commit message after a blank line (`commitAll` takes the whole message). The builder brief (build, repair, fix) gains `Evidence an AC asks to record (listings, renders, counts) goes in <run dir>/evidence.md; the driver appends it to the build commit.` plan.md step 2 gains: an AC that needs recorded evidence names `<spec>.run/evidence.md`, never the commit message. | 04's AC-10 and 05's AC-14 asked for content in a commit message the driver owns; nobody could meet them. |
| D11 | The contract matches the code. docs/v8/interface-contract.md: the fanout row's marks gain `dismissed --lane <id> [--discard]`; the `/spec:fanout` ask row says REPORT ends the turn; the run row gains `--fix "<symptom>"` (lane only) and the `fix(<id>):` commit; § 7's queue table drops `groom` from the subcommand list and the `groom` row; the fanout row says a fix item is a lane. queue.js refuses `--type`/`--after` with no value (`--type needs a value`, exit 2) instead of storing `undefined`. | The contract listed `groom`, which queue.js rejects, and a trailing flag silently did nothing. |
| D12 | Tests pin every criterion by execution in `tests/fanout.test.js`, `tests/run.test.js`, `tests/driver.test.js` and `tests/queue.test.js` on tmp hosts (`host()`, `finish()`, `reusedLane()`), plus one contract grep; existing tests are kept, and the "AUTO … then PLAN picks the third" test adapts to D1's ending line. | The suite is the gate; this brief is a list of drifts. |

## Acceptance Criteria

- **AC-20261105-07-1**: WHEN a batch of two lanes has merged and a third hardened spec and one runnable fix item remain THE SYSTEM SHALL print in REPORT `1 spec(s) and 1 fix(es) left — /clear, then /spec:fanout to continue`; AND WHEN `reported` is marked THE SYSTEM SHALL print the checkpoint and no PLAN body, and the next bare run SHALL print `▶ PLAN` with the third spec as lane 1.
- **AC-20261105-07-2**: WHEN the queue holds a prompt item `/spec:fix specs/20261104/01-alpha.md — RED file left` of type `fix` and spec 01-alpha is `done` with no live lane THE SYSTEM SHALL auto-pick it as a lane named `fix-01-alpha` with worktree `.claude/worktrees/fix-01-alpha` and branch `fix/01-alpha`, and the DISPATCH prompt SHALL be `/spec:run specs/20261104/01-alpha.md --root <wt> --fix 'RED file left'`; WHEN 01-alpha is in a live lane THE SYSTEM SHALL print the fix item under Waiting with why `its spec is in a lane`; WHEN the payload names no spec on disk THE SYSTEM SHALL print it under Waiting with `fix item names no spec on disk`.
- **AC-20261105-07-3**: WHEN a fix lane returns MERGE_READY and lands THE SYSTEM SHALL fast-forward trunk to a commit whose subject is `fix(20261104/01): RED file left`, tick the prompt item (its `done` set), leave the spec's status unchanged, and make no `chore(spec): … done` commit.
- **AC-20261105-07-4**: WHEN `run.js <spec> --root <lane wt> --fix "x"` runs in a fanout lane on a `done` spec THE SYSTEM SHALL open at BUILD with a brief containing `## Fix` and `x` and no `## File Plan`; WHEN it runs outside a lane THE SYSTEM SHALL refuse with exit 2 naming `/spec:fix`.
- **AC-20261105-07-5**: WHEN two lanes are out, lane 1 lands first, and lane 2 returns MERGE_READY with a tree that is green alone but red on top of lane 1's trunk THE SYSTEM SHALL, inside lane 2's `returned` mark, rebase it, run the gate in its worktree, leave trunk's head unchanged, set lane 2 `sent-back` with `lane.red` naming the failing line, rewrite its run state to step `GATE` with `base` = the new merge-base, and print `lane 2 gate red after rebase: <line>` in the re-dispatch body; AND WHEN the lane's `run.js` then goes green and returns MERGE_READY THE SYSTEM SHALL land it on the next `returned`.
- **AC-20261105-07-6**: WHEN a lane's base equals trunk's head at landing THE SYSTEM SHALL run no gate in the lane worktree before the fast-forward (one gate run, on trunk, as today).
- **AC-20261105-07-7**: WHEN the trunk gate is red after a fast-forward THE SYSTEM SHALL print a MERGE_RED body whose first body line starts `first failing line: ` and contains the `RED`-naming line, and a sentence containing `re-run as it is when the failure was a flake`; AND WHEN `gate-repaired` is marked with no new commit after the cause is gone THE SYSTEM SHALL accept it and reach REPORT.
- **AC-20261105-07-8**: WHEN `dismissed --lane 2 --discard` is marked for a dispatched lane holding an uncommitted file THE SYSTEM SHALL leave no worktree at `.claude/worktrees/spec-<stem>` and no branch `spec/<stem>`, print `discarded lane 2 — wip <sha>` under the checkpoint where `<sha>` is a commit reachable from the reflog containing that file, and REPORT SHALL print `dismissed <stem> — worktree and branch removed (wip <sha>)`; WHEN `dismissed --lane 1` is marked at DISPATCH, MERGE_RED and REPORT THE SYSTEM SHALL accept it.
- **AC-20261105-07-9**: WHEN `returned --lane 1` is refused because the main checkout has uncommitted tracked changes, the changes are then committed, and the same mark is re-run THE SYSTEM SHALL land the lane, print a checkpoint line containing `mark returned was already applied` and exit 0.
- **AC-20261105-07-10**: WHEN a driver with an `applied` hook is run with a mark its settled step refuses and `applied` returns false THE SYSTEM SHALL refuse with today's `is not accepted at` message and exit 2.
- **AC-20261105-07-11**: WHEN `spec-fanout.json` is absent and a worktree under `.claude/worktrees/` carries a `fanout` lane marker THE SYSTEM SHALL refuse every bare run and mark with exit 2, naming the worktree and the fanout path, and `cp <backup>` when a `spec-v7-backup/*/spec-fanout.json` exists; WHEN no marker exists THE SYSTEM SHALL plan as today.
- **AC-20261105-07-12**: WHEN a dismissed lane's root spec is `superseded` THE SYSTEM SHALL print `dismissed <stem> — worktree kept at <wt>, spec left hardened in the lane (trunk: superseded)` in REPORT; WHEN a dispatched lane holds an unanswered pending question THE SYSTEM SHALL print ` (question waiting — mark returned)` after that lane in WAIT.
- **AC-20261105-07-13**: WHEN a lane's `<spec>.run/evidence.md` holds `migrations: 18` at COMMIT THE SYSTEM SHALL make the build commit's body contain `migrations: 18`; WHEN the file is absent THE SYSTEM SHALL commit with the subject alone; AND the BUILD brief SHALL contain `evidence.md`.
- **AC-20261105-07-14**: WHEN `queue.js add x --type` or `queue.js add x --after` is run with no following value THE SYSTEM SHALL exit 2 with `needs a value` and add nothing.
- **AC-20261105-07-15**: WHEN `docs/v8/interface-contract.md` is read THE SYSTEM SHALL contain `dismissed --lane <id> [--discard]` and `--fix` in the driver rows, and no `groom` in § 7's queue table; AND `spec/commands/fanout.md` SHALL contain `end the turn` under REPORT and no `continue until the queue drains`.
