# Fix is a driver and every fix is a lane

## Intent
- You asked: plan brief 33 on top of specs 02, 06, 07 and 08 — `/spec:fix` stops being prose and becomes driver-stepped like run, so every question it can raise is a closed kind a lane relays; and a queued `/spec:fix` item with no spec path, only a symptom, is a fix lane too, so fan-out drains every fix item; fewer stops than v7: the fix keeps only the one strings-and-choices stop spec 06 sanctioned.
- I will build:
  - `run.js` runs a fix with or without a spec: `run.js [<spec>] --fix "<symptom>"` as a fanout lane or `--in-place` in the session; a spec-less fix is identified by a slug of its symptom and keeps its run state under the git common dir, so no gitignore line is needed.
  - The fix brief asks the builder to reproduce, state the root cause in one sentence, write the regression test that fails for that reason, fix the cause, and write `fix.json` (cause, test, authored strings and choices, or `needsPlan`); `built` refuses without a cause and a test, and `needsPlan` ends the run by queueing `/spec:plan` with the diagnosis.
  - After the green gate the fix's one stop: when `fix.json` lists user-facing strings or display/policy choices, ESCALATE with `keep` / `revert` / `plan`; in a lane it is a pending question of kind `decision`; an empty list is no stop.
  - The reviewer brief for a fix carries the root cause and the regression test; the commit is `fix(<spec id>|<slug>): <symptom>` with the cause and test in its body; the report is `✅ fixed — <symptom>`.
  - fanout treats every pending `/spec:fix …` item as a lane: spec-bound as spec 07 does, spec-less as `fix-<slug>` with prompt `/spec:run --fix <symptom> --root <wt>`, ordered after the specs, ticked at landing; spec 07's A4 exclusion is lifted.
  - fix.md drives the driver like run.md; builder.md, reviewer.md, doctrine.md, run.md, fanout.md, the interface contract and the architecture notes say so.
- I will not touch:
  - New pending-question kinds: the brief's `fix-dirty-tree`, `fix-decisions`, `fix-dispositions`, `build-blocked`, `scope-widening` have v8 twins already (a dirty tree is a refusal with its remedy; the strings stop is kind `decision`; review dispositions are blocking/advisory/`needs-decision`; a blocked builder is `unmet --decision|--assumption` or `waiting --on`; scope widening is kind `scope` from spec 06). The brief's `derivable: true` is spec 06's written fallback arm plus `📌 Auto-picked`. The brief's worktree-failure ask is already a refusal in `open()`.
  - A second driver file: the fix mode lives in `run.js` (spec 07 D3) so gate, repair, regate, review, spec-edit and scope checks, WIP folding, rebase resolution and landing are one code path.
  - The review severities, FIX_CAP and REPAIR_CAP; `/spec:plan`'s asks; `block-worker-git.sh`; the plugin version (ADR-0039 D4); the queue data model (`type: fix` already exists).
- Architecture or behaviour change: no — a driver gains a spec-less mode and one stop that fix.md already describes in prose; ADR-0039 D1 names the fix lane as the path for small repairs and nothing here departs from an ADR.
- Client sign-off: JJ asked that every `/spec:fix` and `/spec:run` queue item be drained by fan-out and that the fix stay far quieter than v7 — JJ chose: spec-less fix lanes, and only the one authored-strings-and-choices stop (spec 06 D7) survives.

## Goal

A fix, in session or as a lane, walks the same steps every time: reproduce, root cause in one sentence, a regression test that fails for that reason, the fix, the gate, one stop only when the fix authored something the client would notice, a fresh review, one `fix(…)` commit. Nothing about it depends on the session following prose. A queued `/spec:fix` item, with or without a spec path, is a lane fan-out picks after the specs, so a queue of runs and fixes drains to empty without a hand. On the trial, the niko-hub harness fix and shop-bltr's three queued fixes would have run as lanes in the next batch.

## Decisions

| ID | Decision | Why |
|----|----------|-----|
| D1 | `run.js` accepts a spec-less fix: `node run.js --fix "<symptom>" [--in-place] [--root <dir>]` with no spec positional (`makeDriver`'s usage refusal is skipped when `--fix` is present). `specInfo(ctx)` for a spec-less run returns `{abs: null, rel: null, stem: 'fix-<slug>', id: slug}` where `slug = st.slugOf(symptom)`: lowercased, non-alphanumerics to `-`, the first six words joined, at most 40 characters, then `-` and the first six hex characters of `sha1(symptom)`. The run state lives at `st.fixRunPath(root, slug)` = `<git-common-dir>/spec-fix/<slug>.run/state.json`, `runFile` resolves under that dir, and `load`'s gitignore check is skipped for it (nothing under the git dir is tracked). A spec-bound fix (`run.js <spec> --fix …`) keeps spec 07 D3's behaviour and `<spec>.run/`. Outside a fanout lane `--fix` runs only with `--in-place`, else refuses `--fix works in place (--in-place) or as a fanout lane`; the lane-only refusal from spec 07 D3 is replaced by that line. | A fix with no spec has no `specs/…` home; the common dir is shared by every worktree of the host and never tracked, so a lane's state is at one known path and no host edits its .gitignore. |
| D2 | The fix brief is the reproduce-first recipe. `builderBrief(…, 'build')` for a fix prints `## Fix` + symptom (spec 07 D3) followed by: `1. Reproduce it and state the root cause in one sentence before the first edit. 2. Write a regression test that fails for that reason. 3. Fix the cause. 4. Run the test command until green.` then `Write <run dir>/fix.json: {"cause": "<one sentence>", "test": "<file> :: <test name>", "strings": ["<user-facing string you authored>", …], "choices": ["<display or policy choice: hidden, reordered, defaulted, reformatted>", …], "needsPlan": null | "<why the cause needs an architecture or behaviour change>"}. When needsPlan is set, make no edit.` A spec-bound fix also prints the spec's Decisions and ACs as today. `--mark built` on a fix reads `fix.json`; missing, unparsable, or `cause`/`test` blank while `needsPlan` is blank → refused with `fix.json needs cause and test — the builder reproduces first, then fixes`. The parsed fields are stored as `state.fix = {symptom, cause, test, strings, choices}`. | fix.md's six steps become the brief the driver prints, byte for byte in substance; the file is how a builder with no question channel tells the driver what it decided. |
| D3 | `needsPlan` ends the run. `built` with a non-blank `needsPlan` runs `queuePrompt(ctx, '/spec:plan ' + symptom + ' — ' + needsPlan)` (type `plan`), discards any uncommitted change in the worktree (`git.restoreFrom(base)` for tracked files; untracked files the builder added are removed), and ends at step `NEEDS_PLAN` with report `🚫 needs a spec — <needsPlan>` and `📋 queued /spec:plan …`; in a lane the step is an ending like PARKED (fanout's `ENDED` gains `NEEDS_PLAN`; REPORT prints `needs a spec: <stem> — <why>; /spec:plan queued`; the fix item stays pending with `after: {spec: …}` untouched). fix.md's "If the cause needs an architecture or behaviour change, stop before the first edit and offer `/spec:plan`" is this path. | The only architecture or behaviour question a fix can raise is "this is not a fix": the driver records it and hands it to plan, never to the builder. |
| D4 | The one stop. `gateStep` for a fix, after the green gate and the spec-edit and scope checks: when `state.fix.strings.length + state.fix.choices.length > 0` → ESCALATE with `why: 'fix-choices'`, question `fix <id> authored <n> user-facing string(s) and <m> display or policy choice(s): <up to three, "; "-joined>[; +N more]. Keep them?`, options `keep` (recommended; continue to REVIEW), `revert` (one builder round with brief `Undo every listed string and choice back to the pre-fix behaviour; keep the fix and its test:` + the list; marked `fixed`, not counted against FIX_CAP via `state.fixFor = 'choices'`; then GATE, where the lists are re-read from `fix.json` and the stop does not fire again for the same tree), `plan` (D3's ending with `needsPlan = 'the user sent the fix to plan'`). `OFFERED['fix-choices'] = ['keep', 'revert', 'plan']`, `CHOICES` gains `plan`, `KIND_OF['fix-choices'] = 'decision'`. An empty list: no stop, straight to REVIEW. Outside a lane the session asks it with AskUserQuestion like every ESCALATE. | spec 06 D7 wrote this stop as fix.md prose; it is the one fix stop a client-facing developer needs, and JJ wants nothing beyond it. |
| D5 | Review and commit know the fix. The reviewer brief for a fix prints `## Fix`, the symptom, `Root cause: <cause>`, `Regression test: <test>` and `Check that the test fails for the stated cause without the fix and that the fix is at the root, not around the symptom.`; a spec-bound fix also prints the spec's Decisions and ACs as today. COMMIT's subject is `fix(<spec id>): <symptom>` or `fix(<slug>): <symptom>`, its body `Root cause: <cause>` and `Regression test: <test>` lines, then spec 07's evidence. The DONE/MERGE_READY report for a fix is `✅ fixed — <symptom>` with bullets `root cause: …` and `regression test: …`. `--in-place` commits on the current branch as today. | The contract's fix report row (`✅ fixed — {symptom}`: root cause, regression test) and v7's fix row say exactly this. |
| D6 | fanout treats every pending `/spec:fix …` item as a lane. `FIX_RE` becomes `/^\/spec:fix (.+)$/`; when the text matches `^(specs\/\S+\.md)(?: — (.+))?$` the item is spec-bound exactly as spec 07 D2; otherwise it is spec-less: `{fix: true, spec: null, symptom: <text>, slug: st.slugOf(text), item, title: 'fix — <text>'}`, lane `{kind: 'fix', spec: null, symptom, slug, stem: 'fix-<slug>', worktree: '.claude/worktrees/fix-<slug>', branch: 'fix/<slug>', item}`, Agent prompt `/spec:run --fix <symptom> --root <wt>`. A spec-less fix is runnable unless `pending.isLane(<wt>)`, its run state at `st.fixRunPath(root, slug)` has an ENDED step (why `its lane ended <step> — see the report; remove <wt> to run it again`), or its `after` gate is unmet; spec-less fixes come after the spec-bound ones in queue order. `laneRunStep`, `prepare`, `mergeLane`, `finalize` (tick the item, no status, no done commit), WIP and discard read the state through `laneRun(root, lane)` = spec-bound → `<wt>/<spec>.run`, spec-less → `fixRunPath`. The queue's `kindOf`/`pasteLine` are unchanged (`/spec:fix <text>` is already a `fix`-typed prompt). Spec 07's A4 is lifted by this spec. | JJ: fan-out drains every `/spec:fix` and `/spec:run` item. The slug keys the lane the way a stem keys a spec lane. |
| D7 | fix.md drives the driver. It becomes: read doctrine; take the symptom from `$ARGUMENTS` or the conversation, ask only when there is neither; drive `node ${CLAUDE_PLUGIN_ROOT}/scripts/run.js --fix "<symptom>" --in-place` (`--in-place` because a session fix works in the checkout it is in, as today); BUILD/REPAIR/FIX dispatch `spec:builder` with the printed brief and mark as run.md says; ESCALATE: ask the printed question (keep / revert / plan) and mark `escalate <label>`; REVIEW dispatch `spec:reviewer`; the driver gates, commits and reports `✅ fixed — <symptom>` with the root cause and the guarding test; `🚫 needs a spec` ends with `/spec:plan` queued. Frontmatter gains `allowed-tools: Bash(node *), Read, Agent, AskUserQuestion`, `model: opus`, `effort: medium`. | A command that drives a driver has no prose ask left; the three asks the brief named are a refusal, D4's stop and D3's ending. |

## Acceptance Criteria

- **AC-20261105-09-1**: WHEN `node run.js --fix "login button stays disabled after a failed submit" --in-place --root <host>` runs in a non-lane checkout THE SYSTEM SHALL open at BUILD with no spec, a brief containing `## Fix`, the symptom, the four numbered steps and `fix.json`, and a run state at `<git-common-dir>/spec-fix/login-button-stays-disabled-after-a-<6hex>.run/state.json`; WHEN the same command runs without `--in-place` outside a lane THE SYSTEM SHALL refuse with exit 2 and a message containing `--in-place` and `fanout lane`; WHEN `node run.js --fix "x"` is given a spec path too THE SYSTEM SHALL keep the spec-bound behaviour (`<spec>.run/`, the spec's Decisions and ACs in the brief).
- **AC-20261105-09-2**: WHEN `st.slugOf("Login button stays disabled after a failed submit, every time")` is called THE SYSTEM SHALL return `login-button-stays-disabled-after-a-` followed by six lowercase hex characters, at most 47 characters in all; AND two symptoms differing only after the sixth word SHALL yield different slugs.
- **AC-20261105-09-3**: WHEN `--mark built` is run on a fix whose run dir has no `fix.json`, or one whose `cause` or `test` is blank with `needsPlan` blank THE SYSTEM SHALL refuse with exit 2 and `fix.json needs cause and test`; WHEN `fix.json` holds `{"cause": "c", "test": "t.test.js :: guards c", "strings": [], "choices": [], "needsPlan": null}` THE SYSTEM SHALL accept it, store `state.fix.cause` and `state.fix.test`, and go to GATE.
- **AC-20261105-09-4**: WHEN `built` is run on a fix whose `fix.json` has `needsPlan: "the handler needs a new table"` THE SYSTEM SHALL restore the worktree to its base (tracked and untracked edits gone), queue a prompt item `/spec:plan <symptom> — the handler needs a new table` of type `plan`, end at step `NEEDS_PLAN`, and print a report whose outcome line starts `🚫 needs a spec`; AND a second `built` on the same run SHALL be refused as ended.
- **AC-20261105-09-5**: WHEN a fix's gate is green and `fix.json` lists one string and one choice THE SYSTEM SHALL go to ESCALATE with a question containing `authored 1 user-facing string(s) and 1 display or policy choice(s)` and both texts, options `keep`, `revert`, `plan` in that order; AND in a fanout lane THE SYSTEM SHALL write `.claude/pending-question.json` with `kind: "decision"` and print `PENDING_QUESTION`.
- **AC-20261105-09-6**: WHEN the fix-choices question is answered `keep` THE SYSTEM SHALL go to REVIEW with `attempts.fix` unchanged; WHEN answered `revert` THE SYSTEM SHALL print a FIX brief beginning `Undo every listed string and choice` naming both items, and after `fixed` and a green gate with `fix.json` lists empty SHALL go to REVIEW with `attempts.fix` unchanged; WHEN answered `plan` THE SYSTEM SHALL end as in AC-4 with the `/spec:plan` item queued.
- **AC-20261105-09-7**: WHEN a fix's gate is green and `fix.json` lists no strings and no choices THE SYSTEM SHALL go straight to REVIEW with no ESCALATE step in `state.history`.
- **AC-20261105-09-8**: WHEN the reviewer brief for a fix is printed THE SYSTEM SHALL contain `## Fix`, `Root cause: c`, `Regression test: t.test.js :: guards c` and `fails for the stated cause`; AND for a spec-bound fix SHALL also contain the spec's Decisions rows.
- **AC-20261105-09-9**: WHEN a spec-less fix review is clean and COMMIT runs THE SYSTEM SHALL create a commit whose subject is `fix(<slug>): <symptom>` and whose body contains `Root cause: c` and `Regression test: t.test.js :: guards c`; WHEN the fix is spec-bound THE SYSTEM SHALL use `fix(<spec id>): <symptom>`; AND the final report SHALL start `✅ fixed — <symptom>` with bullets `root cause: c` and `regression test: t.test.js :: guards c`.
- **AC-20261105-09-10**: WHEN the queue holds a pending prompt item `/spec:fix login button stays disabled after a failed submit` of type `fix` and no spec item is runnable THE SYSTEM SHALL auto-pick one lane with stem `fix-login-button-stays-disabled-after-a-<6hex>`, worktree `.claude/worktrees/<stem>`, branch `fix/login-button-stays-disabled-after-a-<6hex>`, and a DISPATCH prompt `/spec:run --fix 'login button stays disabled after a failed submit' --root <wt>`; AND WHEN a hardened spec item and a spec-bound fix item are also pending THE SYSTEM SHALL order the lanes spec, spec-bound fix, spec-less fix.
- **AC-20261105-09-11**: WHEN a spec-less fix lane returns MERGE_READY and lands THE SYSTEM SHALL fast-forward trunk to a commit whose subject is `fix(<slug>): <symptom>`, set the item's `done`, flip no spec status, make no `chore(spec): … done` commit, and remove the lane worktree and branch; AND REPORT SHALL print `merged fix-<slug> as <sha>`.
- **AC-20261105-09-12**: WHEN a fix lane's run ends at `NEEDS_PLAN` THE SYSTEM SHALL list the item under Waiting on the next PLAN with `its lane ended NEEDS_PLAN`, leave the item pending, and REPORT SHALL print `needs a spec: fix-<slug> — the handler needs a new table; /spec:plan queued`.
- **AC-20261105-09-13**: WHEN a spec-less fix lane is dismissed with `--discard` THE SYSTEM SHALL remove its worktree, branch and `<git-common-dir>/spec-fix/<slug>.run/` and leave the item pending.
- **AC-20261105-09-14**: WHEN `spec/commands/fix.md` is read THE SYSTEM SHALL contain `run.js --fix` and `--in-place` and no `AskUserQuestion of at most four`; `spec/commands/fanout.md` SHALL contain `fix-<slug>`; `spec/agents/builder.md` SHALL contain `fix.json` and `needsPlan`; `spec/doctrine.md` SHALL contain `keep / revert / plan`; `docs/v8/interface-contract.md` SHALL contain `fix-<slug>`, `NEEDS_PLAN` and `fix-choices`.
