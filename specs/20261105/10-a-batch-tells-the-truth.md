# A batch tells the truth

## Intent
- You asked: plan roadmap 38 — the fix-round findings: ready lanes land while another lane is sent back, every mark prints what it did, a pipe inside backticks survives into the briefs, the spec on trunk says what was built, a brief closes only when the user says so, and the stale doctrine items are settled.
- I will build:
  - WAIT lands a MERGE_READY lane as it returns even while another lane is sent back or resolving a rebase; the sent-back lane rebases onto the live head in its own dispatch and again at landing (spec 07's pre-ff gate).
  - `returned`, `resent`, `dismissed` and `waiting` print, under the checkpoint, what happened to every lane the mark touched: `landed as <sha>`, `sent back — conflicts: <files>` with the Agent call, `gate red after rebase: <line>` with the Agent call, or `held — trunk gate is red`; the WAIT lane list says `resolving rebase` or `gate red after rebase` instead of a stale run step.
  - Table rows in a spec split on `|` outside code spans only (Decisions, File Plan, the lock's restriction check), so a regex or shell pipe in backticks reaches the briefs intact.
  - At COMMIT the driver appends `## As built` to the spec when the builder's `as-built.md`, the review's advisories or files outside the File Plan record a departure; Decisions stay locked.
  - A brief queue item is never ticked by the driver; `queue next` skips a brief whose specs are all done, `queue list` tags it, and the status screen prints one decide line with `/spec:queue done NN`.
- I will not touch:
  - The "doctrine says true things" bullet: v8's `spec/commands/doctor.md` has no numbered checks, no `grounding-contract.md` exists in the plugin, and `genesis.js` has no framework-pricing path; queue item q137 was v7-era and is retired here with no file change.
  - Overlap-aware merge order (specs/20261103/15 D1); anything that asks the user (spec 06); the host environment (spec 08); the fix lane shape, `applied`, evidence and the batch loop (spec 07); `block-worker-git.sh`; the plugin version (ADR-0039 D4).
- Architecture or behaviour change: no — the fan-out landing order, the mark output, the table parser, a spec section the driver appends and the queue's brief rule change exactly as brief 38 specifies; no ADR is added or overturned.
- Client sign-off: whether a brief may leave the queue by itself when its last spec merges (D6 takes that away from the driver, not from a user) — JJ chose no: brief 38 was written from shop-bltr's brief 05 vanishing with its Square steps open and approved as-is in the orchestrator session on 2026-11-05

## Goal

A fan-out batch whose lanes overlap no longer serialises itself: a ready lane lands while a sent-back lane is still resolving, and the resolver pays one more rebase instead of every other lane waiting (spec 06 was rebased three times behind 08, and 08 behind 06, in the fix round). Every mark prints what it did, so an operator never has to run the driver bare to learn a lane was sent back. Briefs quote the spec faithfully, the spec on trunk says what was actually built, and a brief leaves the queue only when the user closes it.

## Decisions

| ID | Decision | Why |
|----|----------|-----|
| D1 | Ready lanes land while one is sent back. `deriveWait` lands the first `done` lane (batch order, one per settle pass) whenever `!s.red`; the two guards — a `sent-back` lane in the batch and a `dispatched` lane mid-rebase — are deleted, and the header comment and architecture note say so. A sent-back lane's own `/spec:run` keeps resolving onto the trunk it was rebased onto; when it returns MERGE_READY its base is older than the moved trunk, so `mergeLane` rebases it again and gates the rebased tree before the fast-forward (spec 07 D4); a new conflict there is a fresh `conflictAt` and sends it back again, and the `second rebase conflict` stop keeps meaning two conflicts against the same trunk head. MERGE_RED still holds every landing until `gate-repaired`. | In the fix round, 08 waited on sent-back 06, then 06 waited on sent-back 08, and 06 was rebased three times; the hold bought nothing the pre-ff gate does not already guarantee. |
| D2 | A mark says what it did. The lane-touching steps (`returned`, `resent`, `dismissed`, `waiting`, `answered`, `resumed`, `gate-repaired`) bump `s.seq` (an integer, 0 when absent) before the step runs; `mergeLane` stamps the lane it worked on with `lane.last = {seq: s.seq, outcome, detail}` where outcome is `landed` (detail: the fast-forward sha), `conflict` (detail: the conflict files) or `red` (detail: the first failing line); a landing skipped because `s.red` is set stamps `held` on every `done` lane with detail `trunk gate is red`. fanout's `after` hook, replacing the discard-only one, prints one line per lane with `last.seq === s.seq`, batch order: `lane N landed as <sha>`, `lane N sent back — conflicts: <a>, <b>`, `lane N gate red after rebase: <line>`, `lane N held — trunk gate is red`; a `sent back` or `gate red` line is followed by the lane's Agent call indented two spaces (the same `agentLine`), so the orchestrator re-sends without a bare run. The discard line stays, printed last. `--json` runs print nothing extra, as today. | A `returned` that sent a lane back, or that landed a different lane, printed only `WAIT → WAIT`; the pilot learned what happened from a bare re-run each time (q174). |
| D3 | WAIT's lane list says what a lane is doing. The lane line's run-step cell is `resolving rebase (<n> files)` for a `sent-back` lane with conflicts or a `dispatched` lane whose worktree `git.rebasing`, `gate red after rebase` for a sent-back lane with `lane.red`, else `laneRunStep` as today; the `(question waiting — mark returned)` suffix is unchanged. | D4 | A table cell keeps its pipes. `lib/state.js` gains `splitCells(line)`: strips one leading and one trailing `|`, then walks the characters splitting on `|` that is neither inside a backtick span (a run of one or more backticks opens a span that the same-length run closes) nor escaped as `\|`; cells are trimmed and `\|` becomes `|`. `decisionRows` and `filePlanTables` use it instead of `split(/(?<!\\)\|/)` / `split('|')`; the File Plan column-binding row and the separator-row test read the same cells. `run.js`'s `stripRows` reads its first cell through `splitCells`. A pipe outside backticks still splits, so no spec written for the old parser changes meaning. `plan.js lock`'s restriction check inherits the fix through `decisionRows`. | Spec 06's D2 carried `` `/\b(cannot|…)\b/i` `` and reached the builder and reviewer briefs cut at the first `|`; the lane fell back to "read the spec file". |
| D5 | The spec on trunk says what was built. `run.js` COMMIT, before the commit, collects departures: every line of `<run dir>/as-built.md` (builder-written, bullets or plain lines, blank lines dropped), every `advisory` finding of `state.review` as `<file>[:<line>] <summary>`, and every path from `outsideFiles` as `touched outside the File Plan: <path>`; when the list is non-empty it appends to the spec in the worktree a `## As built` section (created after the last section when absent) holding one `- ` bullet per departure, prefixed `(fix: <symptom>) ` in a fix lane, deduplicated against bullets already under that heading. The append is written before `commitAll`, so it rides in the build commit. `specEdits` compares Decisions only and `outsidePlan` runs at REVIEW, before the append, so neither sees it; `parseSections` already tolerates an unknown section. The builder brief (build, repair, fix) gains one line naming `<run dir>/as-built.md` for "what you built differently from the spec and why"; builder.md says the same. The reviewer's advisories therefore land in the spec, not only in the chat. | Stale AC strings, renumbered migrations, moved counts and out-of-plan files were accepted as advisories on both hosts and the locked spec silently disagreed with trunk (q173). |

## Acceptance Criteria

- **AC-20261105-10-1**: WHEN three lanes are out, lane 1 has landed, lane 2 returned with a rebase conflict and is `sent-back`, and lane 3 returns MERGE_READY on a tree that does not conflict THE SYSTEM SHALL, inside lane 3's `returned` mark, rebase it, fast-forward trunk to it, tick its queue item and remove its worktree, while lane 2 stays `sent-back`; AND WHEN lane 2's agent resolves, gates and reviews and the lane is marked returned THE SYSTEM SHALL rebase it onto the moved trunk, gate the rebased tree in its worktree (spec 07 D4) and land it on green.
- **AC-20261105-10-2**: WHEN a lane is `dispatched` with a rebase in progress in its worktree and another lane returns MERGE_READY THE SYSTEM SHALL land the returning lane in that mark; AND WHEN the trunk gate is red (`s.red`) and a lane returns MERGE_READY THE SYSTEM SHALL not land it and SHALL print `lane N held — trunk gate is red` under the checkpoint.
- **AC-20261105-10-3**: WHEN a `returned` mark lands lane 3 THE SYSTEM SHALL print, after the checkpoint line, `lane 3 landed as <sha>` where `<sha>` is trunk's new head; WHEN a `returned` mark sends the lane back with a rebase conflict THE SYSTEM SHALL print `lane N sent back — conflicts: <files>` followed on the next line by two spaces and that lane's `Agent({ … })` call; WHEN the pre-ff gate is red THE SYSTEM SHALL print `lane N gate red after rebase: <line>` followed by the Agent call; AND the same mark re-run with `--json` SHALL print none of these lines.
- **AC-20261105-10-4**: WHEN a mark lands two `done` lanes in one settle THE SYSTEM SHALL print one `landed as` line per lane, in batch order, and a lane landed by an earlier mark SHALL not be printed again.
- **AC-20261105-10-5**: WHEN the WAIT body is printed with a `sent-back` lane holding a rebase conflict in two files THE SYSTEM SHALL list it as `lane N — <stem>: sent-back · resolving rebase (2 files)`; WHEN a sent-back lane carries `lane.red` THE SYSTEM SHALL list `gate red after rebase`; WHEN a `dispatched` lane's worktree is mid-rebase THE SYSTEM SHALL list `dispatched · resolving rebase`; AND a dispatched lane with no rebase SHALL list its run step as today.
- **AC-20261105-10-6**: WHEN a Decisions row's cell is `` `/\b(cannot|only \w+ can)\b/i` `` THE SYSTEM SHALL return that row from `decisionRows` with the cell intact and three cells for a three-column row, and the BUILD and REVIEW briefs SHALL contain the cell verbatim; WHEN a File Plan path cell is `` `a|b.js` `` THE SYSTEM SHALL read the path as `a|b.js`; AND a row cell written `a \| b` outside backticks SHALL still read `a | b`.
- **AC-20261105-10-7**: WHEN `splitCells` reads `| x | ``y|z`` | w |` THE SYSTEM SHALL return `['x', '``y|z``', 'w']`; AND WHEN it reads a line whose backtick span is unclosed THE SYSTEM SHALL treat the rest of the line as inside the span.
- **AC-20261105-10-8**: WHEN a lane's `<run dir>/as-built.md` holds `- migration renumbered 0041 → 0047` at COMMIT THE SYSTEM SHALL make the build commit's spec file end with a `## As built` section containing that bullet; WHEN the review recorded an advisory `src/x.js:12 count is now 36` and the diff touched `src/extra.js` outside the File Plan THE SYSTEM SHALL add `- src/x.js:12 count is now 36` and `- touched outside the File Plan: src/extra.js`; AND WHEN none of the three sources has anything THE SYSTEM SHALL leave the spec without the section.
- **AC-20261105-10-9**: WHEN COMMIT runs in a fix lane with `as-built.md` holding one line THE SYSTEM SHALL append the bullet prefixed `(fix: <symptom>) ` under an existing or new `## As built`; AND a bullet already present under the heading SHALL not be appended twice.
- **AC-20261105-10-10**: WHEN a spec gains `## As built` at COMMIT THE SYSTEM SHALL still reach MERGE_READY (lane) or MERGE (in place) with the spec-edit check raising nothing, the BUILD brief of a later run on that spec SHALL print the section through `OTHER_SECTIONS` unchanged, and the builder brief SHALL contain `as-built.md`.
- **AC-20261105-10-11**: WHEN a queued brief item's brief has every member spec `done` THE SYSTEM SHALL keep the item pending across `list`, `next` and `add` writes with no `done` timestamp; `queue next` SHALL skip it and, when nothing else is ready, print `nothing ready — 1 waiting on after gates or finished briefs`; AND `queue list` SHALL end its row with `  ✔ specs done — /spec:queue done NN`.
- **AC-20261105-10-12**: WHEN `queue done NN` is run for that brief THE SYSTEM SHALL tick it; AND a superseded brief's item SHALL list with `  ⛔ superseded — /spec:queue done NN` and stay pending until `done`.
- **AC-20261105-10-13**: WHEN `status.js` runs on a host whose queue holds a brief item for a brief with every spec done THE SYSTEM SHALL print `⚠️ Brief NN (<name>) has every spec done but is still queued.` followed by `   Close it?  /spec:queue done NN` among the decide lines, and `--json` anomalies SHALL include `{kind: "brief-done-queued", audience: "decide"}`; AND the full, bare, empty and all-done golden renders SHALL be byte-identical to today's.
- **AC-20261105-10-14**: WHEN `spec/commands/fanout.md`, `spec/commands/queue.md`, `docs/v8/interface-contract.md` and `docs/v8/architecture.md` are read THE SYSTEM SHALL find `lands as it returns` beside the sent-back case in fanout.md, `lane N landed as` and `As built` in the contract, `brief-done-queued` in the contract and the architecture note, and `✔ specs done` in the contract's `list` row; AND the fanout header comment SHALL no longer say a lane waits while another is sent back or mid-rebase.
- **AC-20261105-10-15**: WHEN the suite runs after this spec THE SYSTEM SHALL pass the rewritten AC-20261105-02-11 test with lane 3 landing while lane 2 is sent back, and the rewritten AC-20261105-04-6 test with brief 03's item still pending, each carrying this spec's AC id beside the old one.
