# The queue item has one owner

## Intent
- You asked: why status and fanout disagree about shop-bltr's q52 (`type: fix` with a bare payload: status pastes it as `/spec:fix …`, fanout skips it and says "queue drained" over six open items) — it is a smell; fix it at the root with the clean structural design and the least tech debt. JJ will run `/spec:migrate` on every repo and uses only v8, never mixed with v7 or earlier.
- I will build:
  - `spec/scripts/lib/queue.js`: the one owner of the queue — the file, the version, the item shape, the type list, creation, dedupe, ticking, reconcile and the paste line. `readQueue`/`writeQueue` leave `lib/state.js`; no other script touches items.
  - One stored shape at queue `version: 3`: `type` is the only carrier of a prompt's command, `payload` is bare text, a spec-bound fix has a real `spec` field. Text is parsed once, at the door (`queue add`, `/spec:migrate`), never on read.
  - `/spec:migrate` converts every existing queue file (versions 1 and 2, including the mixed files real repos hold) to version 3. The reader is strict: any other version is a refusal naming `/spec:migrate`. No tolerant-read code stays behind.
  - fanout picks a fix by `type` and binds it by `spec`; `FIX_RE` and `SPEC_FIX_RE` are deleted.
  - fanout's PLAN and REPORT say "drained" only when zero items are open; otherwise every open item is accounted for exactly once — a lane, waiting with its reason, held, or needing the user with its reason.
  - A gate test: no script outside the owner, the CLI and the migration touches items; one test feeds every real stored shape through `/spec:migrate` and asserts status and fanout agree.
- I will not touch:
  - A shared status/fanout classifier: `lib/next.js` reasons over the roadmap and `eligible()` over worktrees and lanes; they share `work.gateWhy` and, after this spec, one item shape. Nothing is left to drift.
  - A rename of `kind`/`type` to one `action` field: a spec item's action is derived from its status, so it cannot be stored.
  - Normalise-on-read, or any compatibility with an older plugin: JJ runs only v8.
  - The paste lines status prints (the four status goldens stay byte-equal); `queue add`'s flags; the `after` gate rules (spec 04 D5); the brief-closing rule (spec 10 D6); run state's two creators (`run.js:138`, `fanout.js:275`).
  - `block-worker-git.sh`; the plugin version (ADR-0039 D4).
- Architecture or behaviour change: yes — the queue file goes to version 3 with a new item shape and `lib/queue.js` as its only owner (ADR-0042, amending ADR-0041 §1); queue commands refuse an unmigrated repo until `/spec:migrate` runs.
- Client sign-off: how existing queue files convert, and how far the structural fix goes — JJ chose: "I can spec:migrate on every single repo", the clearest structural fix with the least tech debt, v8 only, never mixed with older versions.

## Goal

A queue item means one thing everywhere: status, `queue next`, fanout, run and prototype read the same `type`, `spec` and bare `payload` from one module, so an item that pastes as a fix is a fix lane. Fanout never says "drained" while anything is open. A script that builds an item by hand fails the suite, and an unmigrated queue file stops with its remedy instead of being half-read.

- **AC-20261105-12-2**: WHEN `/spec:migrate --apply` runs on a `version: 1` file holding a spec item with `payload` and no `spec`, a spec item with `spec`, a brief item with `brief`, a prompt with `lane: 'fix'`, a prompt `/spec:plan x` with `ticked: true` and no type, and a prompt `/spec:fix specs/x.md — gate red` THE SYSTEM SHALL write `version: 3` with both spec items' paths in `payload`, the brief's file in `payload`, `{type: 'fix', payload}`, `{type: 'plan', payload: 'x', done}` and `{type: 'fix', spec: 'specs/x.md', payload: 'gate red'}`; AND a second `--apply` SHALL print `✅ nothing to migrate`.

## Assumptions

- A1: The goldens' prompt rows come from `pasteLine` alone, so a byte-equal `paste` keeps them green — if false: the diff names the row and `paste` is corrected, never the golden.
- A2: `st.slugOf` on the bare text equals today's slug of the stripped text (it trims) — if false: `parse` trims as `FIX_RE` did.
- A3: No queue holds a `type: fix` item whose bare text starts with a spec path it does not mean to bind — if false: the migration binds it, which is what the same text typed at `queue add` has always meant (spec 07 D2).
- A4: `genesis.js`'s dedupe moving to open items only changes nothing on a greenfield repo, where genesis runs once — if false: the test shows the double row and genesis keeps a check over done items through `read`.
- A5: The seed-call inventory (`tests/fanout`, `genesis`, `migrate`, `prototype`, `queue`, `run`, `state`, `status`) is a prediction — if another test seeds the queue: move it to the owner in the same batch; never loosen the strict read.
- A6: Spec 11 lands first; its `fanout.js` edits touch neither PLAN's no-lane branch nor REPORT's `next` — if false: rebase on it.
