# The queue travels with the repo

## Intent
- You asked: Sync the queue across my 3 machines by making placed queue items committed files, one per item, under specs/queue/. Each item has a collision-free id (date + 4 hex) and its own rank, so a move changes one file. Every queue write commits that one path. Done on a placed prompt deletes its file; a ticked filled brief or spec keeps a tiny tombstone. All queue reads and writes go through the main checkout, never a lane branch, so an abandoned lane loses nothing and queue files never enter a lane's diff. Take a lock around those commits so parallel lanes cannot collide on the git index. Remove .git/spec-queue.json with format v4 and one /spec:migrate step that moves open items and drops done prompt rows. Add an ADR that amends the common-dir decision.
- I will build:
  - Format v4: one JSON file per placed item at `specs/queue/YYYYMMDD-xxxx.json` with its own rank and no shared sequence, owned by `lib/queue.js`, its storage in a new `lib/queue-files.js`.
  - Every queue read and write resolves the main checkout from any worktree; every write takes the queue lock and commits only its own paths on trunk; a landing's ticks are one commit.
  - Queue commits cost no gate run and break no landing: GATE and `land()` refuse any change a run makes under `specs/queue/`, so the gate cache can ignore those paths, and `land()` and `/spec:release` treat a queue-only trunk move as no move.
  - `/spec:migrate` turns each machine's old queue file into item files, merging with items already pulled, and removes the old file.
- I will not touch:
  - Pushing, pulling or fetching (no script does any), a custom sync ref, and machine-local state: `spec-fanout.json`, `*.run/`, the gate cache, `spec-release.json`.
  - What the queue means: the fill, `after` gates, types, `next`, `list`, `groom` and 05's brief close, except that ids get longer.
  - This repo's own `.git/spec-queue.json`: the build never runs `--apply` here; you migrate each machine after the merge.
- Users will notice: `git pull` brings the other machines' queue; each queue change, and each landing's ticks, is one small `chore(queue): …` commit on trunk, pushed before switching machines; `/spec:queue` writes refuse while the main checkout is off trunk or mid-merge; ids read `20261107-a3f9`, not `q336`.
- You lose: a private per-machine queue (its text becomes repo history) and `qN` ids.
- Architecture or behaviour change: yes — the queue moves from an untracked git-dir file to tracked files on trunk (ADR-0045), and queue writes refuse in some checkout states, needs your yes
- Client sign-off: breaking change to the queue's home and format — yes, approve; queue writes on a side branch or mid-merge — refuse with instructions; queue text visible to everyone on each repo — accept, block secrets, the scan a last line of defence (2026-11-06, kept 2026-11-08); a run's own queue write while the main checkout is off trunk — warn and carry on; a landing's ticks — one commit by default (2026-11-08); every queue write reports its outcome and Next reads it, a missing Next fails loudly — approve (2026-11-08)

## Goal

Run `git push` on one machine and `git pull` on another, and `/spec:queue list` shows the same items in the same order on both. Parallel lanes keep landing with no extra full-suite gate and no failed fast-forward, an abandoned lane loses no queue item, and no `.git/spec-queue.json` remains after `/spec:migrate`.

## Decisions

| ID | Decision | Why |
|----|----------|-----|
| D1 | The queue's home is tracked files under `specs/queue/`: ADR-0045 (accepted 2026-11-06) amends ADR-0042 (the `{version: 3, seq, items[]}` file) and ADR-0044 (what "the file" is) and overturns specs/20260823/08 D1; ADR-0042's single owner and strict read and ADR-0044's "holds what was placed, readers derive the rest" stand. No script pushes, pulls or fetches, there is no custom sync ref, and run and fanout state stay machine-local. | The common dir never leaves a machine. A ref fetched on read would put the network on every read, and `reconcile` would falsely close an item arriving before its unpushed spec. |
| D2 | An open item is `{version: 4, id, rank, kind, type?, spec?, payload, added?, after?}`, a tombstone `{version: 4, id, kind, payload, done}`; `seq` goes. The id is the file stem `YYYYMMDD-xxxx` (local date, 4 random hex, retried while that file exists). `rank` is a decimal string compared numerically, ties broken by id: append is floor(last) + 1, `--top` ceil(first) - 1, and between two items their exact BigInt midpoint, so nothing is ever renumbered. | No shared counter for two machines to race, and a move changes one file. A float runs out after ~50 moves into one gap. A same-day id collision (1 in 65,536) surfaces as a git add/add conflict. |
| D3 | New `lib/queue-files.js` (the wip's, required only by `lib/queue.js`) holds paths, the strict read, rank maths, the D5 check, the lock and the commit; `lib/queue.js` keeps the meaning and its 200-line pin. Every read and write resolves the main checkout with `git.mainRoot(root)` (run.js's `mainRoot` moved into `git.js`, joined with `rev-parse --show-prefix` for `--root`), and `fill` and `reconcile` read spec state there, so `isMain` and `queuePath` go. `Q.write` and `Q.place` go: the write surface is `add`, `tick`, `hold`, `move` and `done`, which absorb the CLI's splice-and-write and place-then-tick. `lib/next.js` `overlay` calls `Q.read` instead of parsing the file, still off in a linked worktree; `queue next` prints the head's own `Q.paste` for every kind. The AC-20261105-12-6 owner list gains `lib/queue-files.js`. | One owner (ADR-0042): the CLI's two direct writes are the only code outside it that knows the layout. A lane's copy of `specs/queue/` is never read or written, so an abandoned lane holds nothing. |
| D4 | Strict reader: any `<git-common-dir>/spec-queue.json` refuses every read, naming `/spec:migrate` (the status screen keeps its migrate line). Every `specs/queue/*.json` must parse, carry version 4 and name its own stem, else the refusal names that file; `.tmp` names are skipped; no directory means no items. | ADR-0042: one migration, no tolerant reads. A git conflict marker lands in an item file and must stop the reader. |
| D5 | A write refuses (exit 2, naming the state and its remedy, nothing written) when the main checkout is not on trunk, is detached, or is mid-merge, mid-rebase, mid-cherry-pick or mid-revert. Reads never refuse on git state; `queue next` and `list` warn on stderr when it is off trunk. [asked: refuse with instructions] | git refuses a partial commit during a merge, and a commit on a side branch would strand the item there. |
| D6 | A write a driver makes as a side effect — `run.js` park and advisories, `lib/land.js`'s ticks, `fanout.js` `Q.hold`, `plan.js` lock's plan-item tick, `prototype.js`'s plan item — goes through `Q.put(root, write, {item, remedy}) → {status: 'written'\|'open'\|'refused', next, warn?}` in `lib/queue.js` (`Q.soft` and every caller's own ternary go): written or open, `next` is that item's own paste line (or its `done` line for a tick); refused under D5, nothing is written, `warn` is `⚠️ not queued — <state>; on <trunk>: /spec:queue add …` (or `done …`), `next` is that trunk command, and the run goes on. The report's Next is `put.next`, never `/spec:queue next` or a re-plan; a refused `Q.hold` loses nothing because PLAN waits a kept lane on its run state's `after`, as it waits an `amend`; `plan.js` lets any error other than a D5 refusal surface; `prototype.js`'s warn joins its report. `lib/report.js` `render()` refuses a missing `next` or one holding `null` or `undefined` (a driver that means "nothing left" says so). [asked: warn and carry on] | v8's `--in-place` builds on a side branch by design, and stopping a finished run over bookkeeping strands it. A spec item still closes through `reconcile` once its done spec reaches trunk. Next read from a stand-in (the add's return, the queue head, a missing value) printed `/spec:plan null` and a false "all done": the outcome is the one fact. |
| D7 | The queue lock is `<git-common-dir>/spec-queue.lock/`, held only by queue writers: the gate slot's pid-file directory (`takeSlot`, lib/host.js) generalised to a name and a limit of 1, 100 ms poll, dead pids cleared, a live holder past 60 s refusing by pid, never nested. Under it a write checks D5, reads fresh, passes each new file through `git.scanFile` (exported; a hit refuses naming the rule, never the text), writes tmp then rename, and runs `git add -- <paths>` and `git commit -q --no-verify -m "chore(queue): <verb> <ids>" -- <paths>` in the main checkout. Every other script git call to that index (`mergeBack`, `commitAll`, `plan.js` and `migrate.js` commits, 01's stub sweep) goes through `git.raw`, which retries a transient `index.lock … File exists` failure every 100 ms for up to 5 s. [asked: accept, block secrets] | Queue writers serialise among themselves. A collision with a merge or commit is a short wait, so one bounded retry in the helper is enough, not a lock around every caller. git takes `index.lock` before it changes anything, so a retry repeats no work. The scan is a last line of defence, not a guarantee: queue text is repo history. A `-- <paths>` commit leaves other staged files as they were (A1). |
| D8 | `git.js` owns `QUEUE_DIR = 'specs/queue'`. GATE (`gateStep`'s tail, beside `buildProof` and `criteriaRed`, so a cache hit still runs it) is red when the run changed anything under it: in a worktree from `merge-base(trunk, HEAD)` to the working tree, in place from HEAD to the working tree, naming each path and the remedy `/spec:queue`. `land()` refuses a rebased branch whose `trunk..HEAD` touches it. With that refusal ahead, `host.js` `OVERLAY` gains it, so `treeSha` and the gate cache ignore it, and in place run.js's scope, nothing-changed and `diff.patch` readers drop paths under it (they are the owner's commits). The queue check runs before the nothing-changed check, so a run that changed only a queue path is red naming it, and `state.commit` is never a queue commit (`queueOnly`). | Hiding the directory everywhere would let a lane's queue edit merge with no gate, scope check or review. Refusing the run's own changes makes ignoring trunk's queue commits safe, so a queue commit between gate and landing is a cache hit, not a full re-run. |
| D9 | New `git.queueOnly(from, to)` is true when every changed path is under `QUEUE_DIR`. In `land()`, a queue-only trunk move, or an `ff-only` merge that failed because one landed, is rebased onto and gated again (a cache hit) without counting toward the three-move refusal, up to 10 such rounds. `land()` works out its spec tick and 05's finished-brief tick before ticking and makes one `Q.tick` call, so one `chore(queue): tick <ids>` commit. `release.js --promote` accepts a record whose sha equals HEAD or is `queueOnly` to it. | `land()`'s round limit and release's sha check both refuse any trunk move, and queue commits would make that routine. The lock no longer spans the merge, so a fast-forward lost to a queue commit is retried rather than refused. One commit per landing keeps trunk quiet. |
| D10 | `reconcile` never writes: its `done` stays in memory, so an item that arrives before its spec reads closed on that machine and comes back when the spec arrives. Dedupe is exact match by key (a brief by number, a spec by path, a prompt by type + spec + payload): the first in rank order is kept, the rest hidden, and any write on an item deletes its open twins in the same commit. `done` on a prompt deletes its file. `done` on brief or spec work writes a tombstone only when the fill would bring the work back, else deletes the file. `done` on a filled item is one write. | Your rule: prefer delete. A tombstone exists only to keep the fill's "a ticked unfinished item comes back last". The same item added on two machines reads as one and closes as one. |
| D11 | `/spec:migrate` is the only converter. A version 1-3 file becomes one item per open row, ranked after any committed item in stored order, with every field kept and the id dated from `added` (today when absent). Done prompt rows are dropped, done brief and spec rows follow D10, and a row matching a committed open item by D10's key is skipped. The old file is deleted last, `backup()` keeps it, and one commit is made: `chore(spec): migrate queue to v4`. Traps: `v7Pending` (migrate.js:294) must exclude every old queue version, an unparseable old file refuses instead of planning nothing, and `--apply` refuses outside the main checkout or under D5; an `--apply` that failed or applied nothing names its remedy as Next, and the apply command reads `/spec:migrate --apply`. | Each machine holds a different queue, so they merge, never overwrite. Today a v3 file would tag `spec-v7-final` and delete `spec-run-cache`, and `readJson` returns null on bad JSON, the false idempotency 6f2858fe fixed. |
| D12 | `genesis.js` drops its `Q.add` loop (line 146). `spec/doctrine.md` § Files, `spec/commands/queue.md` and `migrate.md`, `docs/v8/interface-contract.md` §3 and §7, and `docs/v8/architecture.md` (§2 row, GATE and MERGE rows, queue.js paragraph) name `specs/queue/`, version 4, the GATE refusal, push-before-switching, and the secrets scan as a last line of defence. No test is deleted, and a changed test keeps every AC-ID it cites. | The fill lists every unfinished brief (ADR-0044; 05 keeps a done brief with open steps), and genesis's trunk is not configured yet. The contract docs are what builders read (ADR-0037). ADR-0048's gate keeps cited criteria. |

## Acceptance Criteria

- **AC-20261106-01-1**: WHEN two real clones of one bare origin each add, move and tick items through `queue.js`, then push and pull with plain git THE SYSTEM SHALL print identical `list --json` on both with no conflict and no script having pushed, pulled or fetched; commands and output recorded in `<spec>.run/evidence.md`.
- **AC-20261106-01-2**: WHEN a real lane worktree runs a mark that queues an item THE SYSTEM SHALL commit it on trunk in the main checkout, leave `git status --porcelain` clean there and the lane's diff free of `specs/queue/`; WHEN that lane is abandoned and its worktree removed the item SHALL still be listed.
- **AC-20261106-01-3**: WHEN queue-only commits land on trunk while `land()` gates a lane, three or more times and once between its check and an `ff-only` merge, THE SYSTEM SHALL land it with `cached: true` gates and no refusal, and WHEN a non-queue commit moves trunk three times it SHALL refuse as today; WHEN HEAD moved since the green staging run by queue commits only `--promote` SHALL promote, and on any other path it SHALL refuse as today.
- **AC-20261106-01-4**: WHEN an item is added or moved THE SYSTEM SHALL change exactly one path in one commit, with `--top`, append and 200 moves into one gap all keeping the asked order; WHEN two clones append at the same rank both SHALL list them in id order.
- **AC-20261106-01-5**: WHEN `done` closes a placed prompt THE SYSTEM SHALL delete its file; WHEN it closes unfinished brief or spec work it SHALL leave one tombstone and list the work last; WHEN the work is finished it SHALL delete the file; WHEN one item was added on two clones it SHALL list once and close as one commit; WHEN a landing ticks a placed spec item and its finished brief it SHALL make one queue commit.
- **AC-20261106-01-6**: WHEN a `/spec:queue` write runs with the main checkout on another branch, detached, mid-merge, mid-rebase, mid-cherry-pick or mid-revert THE SYSTEM SHALL exit 2 naming the state and remedy and change nothing; WHEN `list` runs then it SHALL print the items and, off trunk, a warning.
- **AC-20261106-01-7**: WHEN an in-place run on a side branch parks, queues advisories or merges THE SYSTEM SHALL finish its step, write no queue file and print the D6 line with the command to run on trunk; across {park, merge} × {written, open, refused} × {spec, spec-less fix} the printed Next SHALL be `put.next` (the item's own line, or the trunk command when refused), never hold `null`, and never offer `/spec:plan` for a hardened or done spec; WHEN `render()` gets no `next` or one holding `null` THE SYSTEM SHALL throw.
- **AC-20261106-01-8**: WHEN a queue write runs during an in-place run on trunk with uncommitted and staged edits THE SYSTEM SHALL commit only the queue path, leave those edits and staged files as they were, and neither go red nor report the queue path at GATE.
- **AC-20261106-01-9**: WHEN four queue writers run while `land()` merges in the main checkout THE SYSTEM SHALL land every write and the merge with no `index.lock` error; a dead holder's pid SHALL be cleared, a live holder past 60 s SHALL refuse naming it, and an `index.lock` held past 5 s SHALL fail the git call as today.
- **AC-20261106-01-10**: WHEN a lane, a worktree run or an in-place run adds, edits or deletes a file under `specs/queue/` THE SYSTEM SHALL go red at GATE naming the path, including on a cached green gate and when it changed nothing else; WHEN a rebased branch's commits touch it `land()` SHALL refuse and leave trunk unchanged.
- **AC-20261106-01-11**: WHEN `.git/spec-queue.json` exists THE SYSTEM SHALL refuse every queue read naming `/spec:migrate` and the status screen SHALL offer it; WHEN an item file is invalid JSON, another version or misnamed the refusal SHALL name that file.
- **AC-20261106-01-12**: WHEN `--apply` runs on a version 3 file THE SYSTEM SHALL write one file per open item in stored order with every field kept, drop done prompt rows, keep tombstones only under D10, delete the old file, keep a backup and commit once, tag nothing and keep `spec-run-cache`; run on a copy of this repo's real file, counts before and after recorded in `<spec>.run/evidence.md`.
- **AC-20261106-01-13**: WHEN `--apply` runs again THE SYSTEM SHALL print `nothing to migrate`; WHEN a second clone pulls the first's migration and migrates its own file it SHALL add only items not already there, after the existing ranks; WHEN it runs off trunk, in a linked worktree, during a live fan-out or on an unparseable file it SHALL exit 2 and change nothing.
- **AC-20261106-01-14**: WHEN an item's text matches the secrets scan THE SYSTEM SHALL refuse naming the rule without echoing the text, leaving no file or commit; WHEN the host has no git `plan.js lock` SHALL lock with no queue and no error.
- **AC-20261106-01-15**: WHEN `specs/queue/` holds items THE SYSTEM SHALL report nothing for them in `readSpecs`, `status`, `doctor`, 01's stub sweep or 04's criteria read; an item whose spec has not arrived SHALL be hidden without storing that; genesis SHALL write no item file; and the D12 docs SHALL name `specs/queue/` and version 4, never `spec-queue.json` as the live store.

## Assumptions

- A1: `git commit -- <paths>` leaves other staged files staged, is refused mid-merge, and commits a deleted path (documented git; not run while planning, because the worker-git hook blocks git there) — if false: commit through a scratch index plus an index refresh, under the queue lock.
- A2: No host test reads `specs/queue/`, so the gate cache ignoring it hides no test result — if false: that host keeps it in its tree hash and pays a gate run per queue commit; add a config key then.
- A3: Every host pushes trunk directly, with no PR-only protection on it, and the main checkout is never bare — if false: queue commits cannot reach that origin, so ask before upgrading that host.
- A4: One queue commit per write and per landing, beside 01's stub commit, is acceptable trunk noise — if false: fold the landing's tick commit into the stub commit.
- A5: D6's warn line is acted on — if false (follow-ups get lost): add a machine-local spool that the next on-trunk queue write flushes, never a branch commit.
