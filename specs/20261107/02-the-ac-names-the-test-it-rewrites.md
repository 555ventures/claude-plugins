# The AC names the test it rewrites

## Intent
- You asked: Consult with Fable 5.1 — should the test-regrowth issues be addressed too: AC-titled tests piling up beside their `(rewrites AC-…)` siblings, and the reviewer always blocking the deletion of a SHALL CONTINUE TO test? Yes to the approach: the template carries the AC tail pointer again, red-check reads `→ rewrites` tails, and the reviewer unblocks a deletion the own spec's tail names.
- I will build:
  - The spec template's AC line ends `→ writes <file>` again, with the three forms (`writes`, `rewrites <file> :: <title prefix>`, `reuses <file> :: <title prefix>`) named beside it, and `plan.md` step 2 says so.
  - `plan.js lock` refuses an AC without a tail, a `rewrites`/`reuses` tail without `:: <title prefix>`, and a `SHALL CONTINUE TO` criterion whose tail is `rewrites` — each refusal names the AC id and the fix.
  - One tail parser in `lib/state.js` (`acTail`), attached to every parsed AC as `tail`.
  - `red-check.js` takes `--spec <path>` and checks each `→ rewrites <file> :: <prefix>` tail: a test titled `<prefix>…` must exist in `<file>` at base and must be gone (deleted or retitled) at HEAD; a survivor and a prefix the base lacks are reported, advisory, in the reviewer brief next to vacuous green.
  - `reviewer.md`: deleting the test behind a `SHALL CONTINUE TO` criterion stays `blocking` unless an AC of this spec ends `→ rewrites <that file> :: <that title>`.
- I will not touch:
  - Reviewer prose asking it to "name the src line that would fail", a "no tests on migration SQL / versions / dates / hashes / copy" rule, any test-expiry revival, any layer-duplication rule — unverifiable prose or a host-side convention (ADR-0037 keeps guards as scripts).
  - Already locked specs: `hardened`, `implementing`, `done` and `superseded` specs are never re-checked for tails (lock runs once, on a draft); stubs (ADR-0046) are unaffected.
  - `→ reuses` semantics beyond the lock grammar: red-check reads `rewrites` only (a reused title is green on base by design, which the vacuous-green leg already tolerates for CONTINUE TO).
  - The gate, the host test command, the `(pin pN)` cite (it stays before the tail; `pinCoverage` matches it anywhere in the AC text) and the `SHALL CONTINUE TO` exception for new tests passing on base.
- Architecture or behaviour change: no — the tail form is what `docs/v8/interface-contract.md` § spec doc already states; no accepted ADR is departed from. The one behaviour change is a new lock refusal on drafts (D2), asked below.
- Client sign-off: lock refuses a criterion without a test pointer — yes (new drafts only)

## Preparation

Today the tail pointer lives only in `docs/v8/interface-contract.md` line 141; `spec/templates/spec.md`, `spec/commands/plan.md` and `plan.js` are silent, and no v8 script reads it. The result is visible in the repo: of the 54 specs since 2026-11-01, 13 carry tails on every AC (`20261101/01–07`, `20261102/04`, `20261103/01,02,05,07,12`), one is partial (`20261103/13`, 13 of 14) and 40 carry none; the five open hardened specs (`20261106/01–04`, `20261107/01`) carry none and are already locked, so a lock-time rule touches no existing spec here. Host evidence (kaigai 1,461 AC-titled tests over 771 ACs, 89 `(rewrites AC-…)` titles; only 5 of 101 `→ rewrites` pointers left the old title alive, all v7-era) says the pointer worked when a script read it.

`red-check.js` (70 lines) takes `--base --root`, needs `testFileCommand`, checks only test files added since base, returns `{files: [{file, redOnBase, greenOnHead}], vacuousGreen, error?}` and exits 0 always. `run.js` `redCheck(state, wt)` runs it once per green tree only when `cfg.testFileCommand` is set, folds the JSON into one string `state.redCheck` (`red-check: vacuous green — … pass on base too` / `red-check: N new test file(s), none vacuous` / `red-check: no verdict (…)`), and `reviewerBrief` prints that string as one brief line. The brief already lists every AC with its full text, so a tail in an AC reaches the reviewer unchanged. `lib/state.js` `parseAcs` keeps the whole bullet text (continuation lines joined) and no field for the tail.

Fixtures that lock a spec: `tests/plan.test.js` `fresh` (template placeholders → `x`, so a template tail `→ writes <file>` becomes `→ writes x`, which passes) and `protoSpec` (replaces the AC line with bare AC sentences — no tails, refused by D2 without a fix), `tests/integration.test.js` (replaces the AC sentence, keeps the tail), `tests/queue.test.js` AC-20261105-12-3 (placeholders → `x`). `tests/run.test.js` AC-20261105-15-11 pins the reviewer sentence; after `20261107/01` it ends at "is `blocking`". `tests/init.test.js` AC-20261105-17-15 asserts the contract doc does not contain `vacuous-pass`.

## Goal

Every AC of a new spec names the test file it writes, rewrites or reuses, and the lock refuses one that does not. When a spec says it rewrites a test, red-check tells the reviewer whether the old title actually left, and the reviewer no longer blocks the deletion that the spec itself promised. The `(rewrites AC-…)` pile-up stops growing because a rewrite is now a checked claim, not a title convention.

## Acceptance Criteria

- **AC-20261107-02-1**: WHEN `readSpec` parses `- **AC-X-01-1**: WHEN a THE SYSTEM SHALL b (pin p2). → rewrites tests/a.test.js :: AC-X-00-3 old title` and `… SHALL c. → writes tests/b.test.js` and `… SHALL d.` THE SYSTEM SHALL return `tail` `{verb: 'rewrites', file: 'tests/a.test.js', prefix: 'AC-X-00-3 old title'}`, `{verb: 'writes', file: 'tests/b.test.js', prefix: null}` and `null`, with each AC's `text` unchanged. → writes tests/state.test.js
- **AC-20261107-02-2**: WHEN `plan.js lock` runs on a draft whose ACs are one with no tail, one `→ rewrites tests/a.test.js` without `::` and one `SHALL CONTINUE TO … → rewrites tests/a.test.js :: t` THE SYSTEM SHALL exit 2, name all three ids with their fix in one message, and leave `status: draft`; and WHEN each is corrected (`→ writes`, `:: t`, `→ reuses`) THE SYSTEM SHALL lock. → writes tests/plan.test.js
- **AC-20261107-02-3**: WHEN a filled template (`fresh`) and a `prototype:` spec whose ACs end `(pin p1). → writes x` are locked THE SYSTEM SHALL CONTINUE TO lock them, and the pin-coverage refusal SHALL CONTINUE TO name an uncovered pin by id. → reuses tests/plan.test.js :: AC-20261105-14-8 a behaviour pin with no (pin pN) AC refuses the lock by id
- **AC-20261107-02-4**: WHEN `red-check.js --base <b> --root <r> --spec <s>` runs with a spec whose AC ends `→ rewrites test/a.test.js :: AC-X-00-3 old` and the base file holds `test('AC-X-00-3 old title', …)` THE SYSTEM SHALL report `rewrites: [{file: 'test/a.test.js', prefix: 'AC-X-00-3 old', onBase: true, survives: true}]` when HEAD still holds that title, `survives: false` when HEAD retitles it to `AC-X-02-1 new (rewrites AC-X-00-3)` or deletes the file, and `onBase: false` when the base file has no such title; exit 0 in every case. → writes tests/red-check.test.js
- **AC-20261107-02-5**: WHEN the HEAD file holds the title only inside a `//` or `/* */` comment, or holds it after a double quote or a backtick instead of a single quote THE SYSTEM SHALL report `survives: false` for the commented one and `true` for each quote form. → writes tests/red-check.test.js
- **AC-20261107-02-6**: WHEN red-check runs without `testFileCommand` on a spec with a `rewrites` tail and no new test file THE SYSTEM SHALL report `rewrites` with no `error`; and WHEN a new test file exists without `testFileCommand` THE SYSTEM SHALL CONTINUE TO report the error. → rewrites tests/red-check.test.js :: without testFileCommand it reports an error and still exits 0

- **AC-20261107-02-8**: WHEN the same run also has a vacuous new test under `testFileCommand` THE SYSTEM SHALL print the vacuous-green line and the survivor line as two `red-check:` lines of the brief; and WHEN the spec has no `rewrites` tail and the config no `testFileCommand` THE SYSTEM SHALL CONTINUE TO print no `red-check` line. → rewrites tests/run.test.js :: AC-20261105-15-4 without testFileCommand red-check does not run and the brief has no such line
