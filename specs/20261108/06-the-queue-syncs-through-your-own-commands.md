# The queue syncs through your own commands

## Intent
- You asked: Sync the queue across my 3 machines: placed items as committed files, one per item under specs/queue/, each with a collision-free id (date + 4 hex) and its own rank so a move changes one file (20261106/01); then, redesigned 2026-11-08, only my own `/spec:queue add|move|done` commits queue state and driver-created items stay in the machine-local file.
- I will build:
  - Your items as tracked files under `specs/queue/`, written and committed only by your `/spec:queue add|move|done`; driver items in the machine-local file; one ordered list from both (ADR-0050).
  - Drivers that never write a tracked path and never tick: every close is read from trunk (a spec's status, a finished brief, a `Queue: <id>` trailer on the fix or lock commit that finished it).
  - Queue commits that cost no full gate: the gate cache, a run's diff and `--promote` ignore `specs/queue/`.
  - `/spec:migrate` turning each machine's old file into tracked items with new ids, and doctrine § Files plus the queue, migrate and fix commands and contract docs saying so.
- I will not touch:
  - Pushing, pulling or fetching (no script does any), a queue lock, retries in `git.raw`, `land()`'s move rule, and machine-local run, fanout, gate-cache and release state.
  - What the queue means otherwise: the fill, `after` gates, types, `next`, `list`'s row format, `groom`.
- Users will notice: `git pull` brings your other machines' queue; each `add`, `move` or `done` on your items is one `chore(queue): …` commit on trunk (push before switching machines) and refuses with its fix while the main checkout is off trunk or mid-merge; items a run, fanout or prototype queues stay on the machine that made them; ids read `20261108-a3f9`, not `q344`; a queued brief whose specs are done with no open step leaves the queue by itself; a fix's item closes once its commit is on trunk.
- You lose: privacy of the items you place (their text becomes repo history), `qN` ids, and the "Close it?" line for a finished queued brief.
- Architecture or behaviour change: yes — the queue splits into tracked files on trunk for your items and the machine-local file for drivers' items (ADR-0050, superseding ADR-0045), and no driver ticks an item any more, needs your yes
- Client sign-off: queue sync design — approve the split: only your commands commit, driver items stay local (2026-11-08); kept from 2026-11-06: queue writes off trunk or mid-merge — refuse with instructions; queue text in repo history — accept, block secrets; migration — move every open item (2026-11-08); a done queued brief with no open step — closes by itself (2026-11-08)

## Goal

Run `git push` on one machine and `git pull` on another, and `/spec:queue list` shows the items you placed in the same order on both, and an item a run closed on either machine reads closed on both once trunk is pulled, and a machine that has pulled never drains it again. No driver writes a path under `specs/queue/`, a queue commit costs a landing no full gate, and after `/spec:migrate` no machine holds a version 3 file.

| D1 | Two stores, one owner: ADR-0050 (accepted 2026-11-08) supersedes ADR-0045 and amends ADR-0042 (the file) and ADR-0044 ("the file"); their single owner, strict read and "holds what was placed, readers derive the rest" stand. An item you place is a tracked file `specs/queue/<id>.json` in the main checkout (`git.mainRoot` from tag `spec-01-queue-wip-2`; run.js's `mainRoot` moves into git.js); a driver's stays in `<git-common-dir>/spec-queue.json`, now `{version: 4, items[], holds{}}`. ## Acceptance Criteria

- **AC-20261108-06-1**: WHEN two real clones of one bare origin each add, move and close items through `queue.js`, then push and pull with plain git THE SYSTEM SHALL print the same tracked items in the same order in `list --json` on both, each write one commit touching only its own paths and no script having pushed, pulled or fetched; commands and output recorded in `<spec>.run/evidence.md`.
- **AC-20261108-06-2**: WHEN `queue.js add` runs with `--root` a lane worktree THE SYSTEM SHALL commit the item on trunk in the main checkout, leaving `git status --porcelain` clean there and the lane's diff free of `specs/queue/`.
- **AC-20261108-06-3**: WHEN `add`, or `move` or `done` on a tracked item, runs with the main checkout on another branch, detached, mid-merge, mid-rebase, mid-cherry-pick or mid-revert THE SYSTEM SHALL exit 2 naming the state and its remedy and change no file; WHEN its `git commit` fails it SHALL put its paths back and print git's message; WHEN `list` runs then it SHALL print the items.
- **AC-20261108-06-4**: WHEN items are added, added `--top` and moved 200 times into one gap THE SYSTEM SHALL keep the asked order and change one path per add or move, and SHALL list two same-rank items from two clones in id order; WHEN `move` targets a local item it SHALL re-rank it in the local file with no commit, and a filled item SHALL become one tracked file.
- **AC-20261108-06-5**: WHEN `done` closes a tracked prompt THE SYSTEM SHALL delete its file, on unfinished brief or spec work leave one tombstone listed last, and on finished work delete the file; WHEN any tracked write runs it SHALL delete in that commit every tracked file D5 reads done and keep a spec item whose spec file is missing.
- **AC-20261108-06-6**: WHEN the local file is version 1, 2 or 3 THE SYSTEM SHALL refuse every queue read naming `/spec:migrate` and the status screen SHALL offer it; WHEN a tracked file is invalid JSON, another version, misnamed or open with no rank the refusal SHALL name that file.
- **AC-20261108-06-7**: WHEN a run parks with a fix, plan or decide item, queues advisories, prototype queues its plan item, genesis writes its roadmap, or fanout holds a lane on a tracked item, on trunk and off it, THE SYSTEM SHALL change only `spec-queue.json`, make no commit and list the held item `⏳ after …`, and drop the hold once that id is gone; AND the owner test SHALL report a copy of `fanout.js` that calls `Q.done`.
- **AC-20261108-06-8**: WHEN a brief's specs are all done or superseded with no open step THE SYSTEM SHALL read its tracked or local item done after a worktree landing, an in-place run, a supersede or a box ticked later, print no `Close it?` line for it, and list it again once a box is opened; a worktree landing SHALL still print the `📌 auto-closed` line.
- **AC-20261108-06-9**: WHEN an in-place fix and a fanout fix lane finish queued fix items THE SYSTEM SHALL end each fix commit with `Queue: <id>` (the lane's from its batch row, even with a retyped symptom) and, under each `mergeStrategy`, trunk SHALL carry it; WHEN a second clone pulls that trunk it SHALL read the tracked item done and its fanout SHALL not drain it; WHEN the trailer is only on a side branch the item SHALL stay open until that branch merges; WHEN `plan.js lock` covers every behaviour pin its lock commit SHALL name the plan item and print `📋 plan item closed`.
- **AC-20261108-06-10**: WHEN a queue commit lands on trunk while `land()` gates a lane THE SYSTEM SHALL land it with the second gate `cached: true` and no refusal; WHEN one lands during an in-place run on trunk its `diff.patch`, outside-plan files and build commit SHALL hold no queue path; WHEN a builder edits a file under `specs/queue/` no run commit SHALL hold it and the lane SHALL still land; WHEN HEAD moved since the green staging run by queue commits only `--promote` SHALL promote, and otherwise refuse as today.
- **AC-20261108-06-11**: WHEN `--apply` runs on a copy of this repo's real version 3 file THE SYSTEM SHALL write one tracked file per open row and per tombstone of unfinished work, in stored order with every field kept and a new id, drop done prompts, rewrite the local file as version 4 with no items, keep a backup, print each `qN → <id>`, commit once, tag nothing and keep `spec-run-cache`; counts before and after recorded in `<spec>.run/evidence.md`.
- **AC-20261108-06-12**: WHEN `--apply` runs again THE SYSTEM SHALL print `nothing to migrate`; WHEN a second clone pulls the first's migration and migrates its own file it SHALL add only rows not already there, after the existing ranks; WHEN it runs off trunk, in a linked worktree, during a live fan-out or on an unparseable file it SHALL exit 2 and change nothing; a version 1 or 2 file SHALL reach version 4 in one run.
- **AC-20261108-06-13**: WHEN an added item's text matches the secrets scan THE SYSTEM SHALL refuse naming the rule without echoing the text, leaving no file and no commit.
- **AC-20261108-06-14**: WHEN the D9 docs are grepped THE SYSTEM SHALL find `specs/queue/`, version 4, both stores and the `Queue:` trailer, and no `{version: 3, seq` as the live shape.

## Assumptions

- A1: `git commit -- <paths>` commits only those paths, leaves other staged files staged and is refused mid-merge (documented git) — if false: commit through a scratch index.
- A2: No host test or build reads `specs/queue/`, so the gate cache and `--promote` ignoring it hide nothing — if false: that host keeps it in its tree hash and pays a gate run per queue commit.
- A3: Two queue writes, or a queue write and a landing's `mergeBack`, in the same few milliseconds are rare enough that the loser failing with git's message and nothing changed is acceptable — if false: a lock among queue writers only, never spanning a merge.
- A4: Every host's trunk takes direct pushes, and 20261108/05 (draft) re-plans its "landing ticks the fix item" as D6's `state.item` trailer — if false: queue commits cannot reach that origin (ask), or 05 would tick a tracked item.
